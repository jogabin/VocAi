# ADR-005 요건정리 에이전트

- 상태: 채택
- 날짜: 2026-10-23

## 요약

요건정리는 확정된 범위(`scope.md`)를 읽고, 화면 탭별로 "누가 무엇을 할 수 있어야 하나"를 업무 말로 쓰는 단계입니다.  
탭 목록부터 정하고, 어떻게 쓰고 확인받을지는 안을 보여 주고 사람이 고르게 합니다.  
이번 프로젝트에서는 탭마다 초안을 보여 주고 고칠 곳을 받는 방식을 골랐습니다(2026-10-23).  
요건은 탭마다 파일 하나에 남기고, 파일마다 사람이 확인하면 확정됩니다(② 요건 확정).  
아키텍처와 디자인은 작성 중인 파일로도 초안을 쓰지만, 확정은 요건 파일이 모두 확정된 뒤에 합니다(2026-10-24 바뀐 약속, ADR-006).

```
확정된 scope.md와 참고 자료를 읽는다 (확정이 아니면 시작하지 않음)
  ↓
사용자, 탭 목록, 공통 요건의 뼈대를 보여 주고 확인받는다 → requirements.md를 만든다 (작성 중)
  ↓
진행 방식을 고르게 한다 (탭마다 초안 / 질문지 먼저 / 전부 쓰고 한 번에)
  ↓
고른 방식대로 공통 요건부터 초안을 쓰고 보여 준다 → 고칠 곳과 질문의 답을 받는다
  ↓
정리한 사람이 확인하면 확인 대기 → 팀 검토용 사본을 올릴지 묻는다
  ↓
팀이 확인하면 확정 → 아키텍처·디자인으로
```

```
docs/requirements/
├── scope.md                   인터뷰가 남김 (확정)
├── requirements.md            사용자, 탭 목록과 탭별 상태, 공통 요건
└── tabs/
    ├── 01-<탭 이름>.md        탭 1의 요건 (상태는 파일마다)
    └── 02-<탭 이름>.md
```

요건과 설계의 경계는 이렇게 정했습니다.

| 요건정리가 쓰는 것 | 쓰지 않는 것 (넘길 단계) |
|---|---|
| 누가 무엇을 할 수 있어야 하나 | 데이터 구조, 저장 방식, 시스템 연결, AI를 어떻게 만드나 (아키텍처) |
| AI나 시스템이 무엇을, 어떤 기준으로 하나 | 화면 모양, 배치, 색 (디자인) |
| 업무 규칙과 수치 (수치는 출처와 함께) | 버튼과 화면 이동, 빈 화면과 오류 표시, 서버에 무엇을 요청하나 (스펙) |
| 우선순위 (꼭, 나중) | 파일과 코드 (구현 계획) |

비개발자가 회의에서 "맞다, 아니다"를 말할 수 있으면 요건입니다.  
같은 요건을 화면 조작이나 데이터로 여러 방법으로 만들 수 있다면, 그 방법은 뒤 단계에서 정합니다.

- 범위가 다시 확정되면, 읽었던 때와 비교해 걸리는 요건만 고칩니다(에이전트 사이의 약속).
- 시험 장면은 8개이고, 「결정」 8번에 있습니다.

자세한 내용은 아래 「결정」에 있습니다.

## 배경

ADR-002에서 정한 개발 에이전트 10개 가운데 두 번째인 요건정리 에이전트(`sdd-analyst`)를 만듭니다.  
ADR-003의 만드는 순서에서 첫 단계(에이전트 ADR 쓰기)에 해당합니다.

인터뷰(ADR-004)는 요건을 쓰지 않고, 범위와 큰 갈림길만 정합니다.  
세부 요건은 `scope.md`의 「다른 단계로 넘길 것」에 "요건정리"로 넘겨 둡니다.  
요건정리는 정해진 범위와 넘겨받은 것을 바탕으로 요건을 씁니다.

요건정의서는 비개발자와 화면 탭별로 회의할 수 있게 쓰기로 했습니다(10/14 확인, 진행 설계 메모 R8·D10).  
그래서 요건은 업무 말로 쓰고, 화면 탭별로 나눕니다.

이 단계에서 함께 정할 것이 두 가지 있습니다.

- ADR-002 「주의할 점」은 "탭별로 나눠 쓸 때 파일 이름을 어떻게 붙일지는 요건정리 에이전트를 만들 때 정한다"고 남겨 두었습니다.
- 요건과 설계의 경계가 정해져 있지 않습니다.  
  [SDD 한눈에 보기](../guide/sdd.md)는 아키텍처, 디자인, 스펙, 구현 계획의 차이만 보여 줍니다.  
  경계가 없으면 요건정리가 화면 동작까지 써서 스펙과 겹치거나, 업무 규칙을 비워 둬서 스펙으로 밀립니다.

## 정할 것

ADR-003의 「에이전트 ADR에 쓸 것」 8가지를 정합니다.

| 항목 | 무엇을 정하나 | 지금 아는 것 |
|---|---|---|
| 1. 하는 일 | 요건정리가 쓰는 것과 쓰지 않는 것 | **질문 2** |
| 2. 읽는 것 | 무엇을 읽고 시작하나 | 확정된 `scope.md`와 거기 적힌 참고 자료 (ADR-003 약속, ADR-004) |
| 3. 남기는 것 | 요건정의서의 모양 | **질문 1** |
| 4. 대화 순서 | 어떻게 묻고 쓰나 | **질문 3** |
| 5. 사람 확인 | 누가 확정하나 | 정리한 사람이 먼저 보고, 팀 회의에서 팀원이 확인 (ADR-002 ②)<br>팀 검토 방식은 **질문 4** |
| 6. 지킬 것 | 하면 안 되는 것 | 저장소 규칙, 에이전트 사이의 약속 |
| 7. 다음 단계로 넘기기 | 아키텍처와 디자인이 무엇을 이어받나 | 확정된 문서만 넘김 (ADR-003 약속) |
| 8. 시험 장면 | 3개 이상, 각각 무엇이 나오면 통과인지 | 아직 정하지 않음 |

## 질문 1. 요건정의서를 어떻게 나누나

### 지켜야 할 조건

1. 비개발자와 화면 탭별로 회의할 수 있습니다.
2. 끝난 탭부터 다음 단계로 넘길 수 있습니다(ADR-002 조건 4).  
   ADR-002는 단계를 전체에 한 번 할지 탭마다 할지 에이전트에 정해 두지 않기로 했습니다.
3. 화면 탭에 속하지 않는 일도 빠지지 않습니다.  
   예를 들어 상담이 들어오면 자동으로 판단하고 알리는 일은 어느 한 탭의 일이 아닙니다.
4. 다음 단계가 무엇을 읽어도 되는지 헷갈리지 않습니다.

세 안을 같은 예(탭 3개)로 보여 줍니다. 탭 이름은 설명을 위해 지어낸 것입니다.  
안 1과 안 2에서 `requirements.md` 아래에 달린 줄은 파일이 아니라 그 파일 안의 장입니다.

### 안 1. 한 파일, 탭마다 장

```
docs/requirements/
├── scope.md
└── requirements.md         상태: 작성 중 (파일 전체에 하나)
    ├── 탭 목록
    ├── 0. 공통
    ├── 1. 상담등록
    ├── 2. 장애목록
    └── 3. 기준관리
```

| 구분 | 내용 |
|---|---|
| 장점 | ADR-002의 파일 표(`requirements.md` 하나)와 같습니다.<br>파일과 상태가 하나라서 관리가 쉽습니다. |
| 단점 | 상태가 하나라서, 탭 하나를 고치면 파일 전체가 확인 대기로 돌아갑니다.<br>끝난 탭만 먼저 확정해 넘길 수 없습니다. |
| 결과 | 조건 1, 3, 4는 지킵니다.<br>조건 2는 지키지 못합니다. |

### 안 2. 한 파일, 탭마다 상태

안 1에 더해, 탭 목록 표에 탭마다 상태를 둡니다.

```
docs/requirements/
├── scope.md
└── requirements.md         상태: 작성 중 (파일 전체)
    ├── 탭 목록             탭마다 상태 칸이 있음
    ├── 0. 공통
    ├── 1. 상담등록         상태: 확정
    ├── 2. 장애목록         상태: 확인 대기
    └── 3. 기준관리         상태: 작성 중
```

| 구분 | 내용 |
|---|---|
| 장점 | 파일은 하나이면서 끝난 탭부터 넘길 수 있습니다. |
| 단점 | 파일 맨 위의 상태와 탭별 상태가 한 파일에 섞여서, 다음 단계가 어디까지 읽어도 되는지 헷갈립니다.<br>에이전트 사이의 약속("문서 맨 위에 상태")과도 어긋납니다. |
| 결과 | 조건 1~3은 지킵니다.<br>조건 4는 일부만 지킵니다. |

### 안 3. 탭마다 파일

`requirements.md`에는 사용자, 탭 목록, 공통 요건을 두고, 탭은 `tabs/` 아래에 파일을 따로 둡니다.  
파일마다 맨 위에 상태가 있습니다.

```
docs/requirements/
├── scope.md
├── requirements.md         상태: 확정 (사용자, 탭 목록과 탭별 상태, 0. 공통)
└── tabs/
    ├── 01-상담등록.md      상태: 확정
    ├── 02-장애목록.md      상태: 확인 대기
    └── 03-기준관리.md      상태: 작성 중
```

| 구분 | 내용 |
|---|---|
| 장점 | 탭마다 회의하고, 확정하고, 팀 검토용 사본을 올리기 쉽습니다.<br>탭 하나를 고쳐도 다른 탭의 확정은 그대로입니다.<br>파일마다 맨 위에 상태가 있어서 에이전트 사이의 약속과 같습니다. |
| 단점 | 파일과 상태가 여러 개입니다.<br>그래서 `requirements.md`의 탭 목록에 탭별 상태를 모아 보여 줍니다. 원본은 탭 파일 맨 위의 상태입니다.<br>ADR-002의 파일 표와 달라집니다. ADR-002가 이 ADR로 미뤄 둔 것이므로, `sdd.md`의 표를 이 ADR에 맞춥니다. |
| 결과 | 네 조건을 모두 지킵니다. |

### 한눈에 비교

| | 안 1 | 안 2 | 안 3 |
|---|---|---|---|
| 조건 1. 탭별 회의 | ○ | ○ | ○ |
| 조건 2. 끝난 탭부터 넘김 | ✗ 상태가 하나 | ○ | ○ |
| 조건 3. 탭 밖의 일도 담음 | ○ 공통 장 | ○ 공통 장 | ○ `requirements.md` |
| 조건 4. 다음 단계가 읽을 것이 분명함 | ○ | △ 상태가 섞임 | ○ |
| (참고) 관리할 파일이 적음 | ○ | ○ | ✗ |

처음에는 안 1을 추천했습니다. 다음 단계인 아키텍처와 디자인이 어차피 전체를 읽기 때문입니다.  
검토하면서 탭별 회의, 탭별 확정, 끝난 탭부터 넘기기를 함께 보니 네 조건을 모두 지키는 안은 안 3뿐이었습니다.  
그래서 안 3으로 정했습니다.

## 질문 2. 요건정리는 어디까지 쓰나

요건과 설계의 경계를 정하는 질문입니다.

### 지켜야 할 조건

1. 비개발자가 읽고 맞는지 판단할 수 있습니다.
2. 뒤 단계(아키텍처, 디자인, 스펙)와 일이 겹치지 않습니다.
3. 사람이 정해야 할 것(업무 규칙, 수치)이 뒤 단계로 밀리지 않습니다.

### 안 A. 업무 말로 "무엇을"까지

누가 무엇을 할 수 있어야 하나, 업무 규칙과 수치, 우선순위까지 씁니다.  
화면 동작, 데이터 구조, 화면 모양은 쓰지 않습니다.

| 구분 | 내용 |
|---|---|
| 장점 | 비개발자가 회의에서 판단할 수 있는 것만 담깁니다.<br>등급 조건, 알림 대상 같은 업무 규칙을 요건 단계에서 사람이 정합니다. |
| 단점 | 업무 규칙과 화면 동작의 경계가 애매한 곳이 생깁니다.<br>「결정」 1번의 판단 기준과 예로 나눕니다. |
| 결과 | 세 조건을 모두 지킵니다. |

### 안 B. 화면 동작까지

버튼을 누르면 무엇이 열리는지, 빈 화면은 어떻게 보이는지까지 씁니다.  
v2 기능 명세서의 방식입니다.

| 구분 | 내용 |
|---|---|
| 장점 | 스펙이 할 일이 줄어듭니다. |
| 단점 | 스펙과 일이 겹칩니다.<br>화면 동작은 아키텍처와 시안을 보고 정해야 하는데, 그보다 먼저 정하게 됩니다.<br>버튼과 화면 이동이 섞이면 비개발자가 볼 양이 늘어납니다. |
| 결과 | 조건 3은 지킵니다.<br>조건 1은 일부만, 조건 2는 지키지 못합니다. |

### 안 C. 기능 목록만

기능 이름만 적고, 업무 규칙과 수치는 스펙에서 정합니다.

| 구분 | 내용 |
|---|---|
| 장점 | 요건정의서가 짧아집니다. |
| 단점 | 업무 규칙과 수치를 스펙에서 정하게 됩니다.<br>스펙은 비개발자와 회의하는 문서가 아니라서, 사람이 정할 것을 AI가 정하게 될 수 있습니다. |
| 결과 | 조건 1과 2는 지킵니다.<br>조건 3은 지키지 못합니다. |

### 한눈에 비교

| | 안 A | 안 B | 안 C |
|---|---|---|---|
| 조건 1. 비개발자가 판단함 | ○ | △ 화면 동작이 섞임 | ○ |
| 조건 2. 뒤 단계와 안 겹침 | ○ | ✗ 스펙과 겹침 | ○ |
| 조건 3. 업무 규칙을 사람이 정함 | ○ | ○ | ✗ 스펙으로 밀림 |

## 질문 3. 어떻게 묻고 쓰나

### 지켜야 할 조건

1. `scope.md`에서 정한 것은 다시 묻지 않습니다(에이전트 사이의 약속).
2. 사람이 한 번에 볼 양이 적습니다(ADR-002 조건 5).
3. 근거가 없는 것을 짐작으로 채우지 않습니다(에이전트 사이의 약속).

### 안 가. 탭 목록부터 정하고, 탭마다 초안을 보여 주기

사용자와 탭 목록, 공통 요건의 뼈대를 먼저 확인받습니다.  
그다음 공통 요건과 탭마다 초안을 써서 보여 주고, 고칠 곳과 질문의 답만 받습니다.

| 구분 | 내용 |
|---|---|
| 장점 | 큰 갈림길은 인터뷰에서 정했고 남은 것은 세부라서, 초안을 보고 판단하는 쪽이 빠릅니다.<br>한 번에 탭 하나만 봅니다.<br>근거가 없는 칸은 질문으로 올라옵니다. |
| 단점 | 초안이 틀린 방향이면 고칠 것이 많아집니다.<br>그래서 탭 목록과 뼈대를 먼저 확인받습니다. |
| 결과 | 세 조건을 모두 지킵니다. |

### 안 나. 질문지를 먼저 만들어 묻기

인터뷰처럼 질문지를 만들어 다 묻고 나서 씁니다.

| 구분 | 내용 |
|---|---|
| 장점 | 빠뜨리는 것이 적습니다. |
| 단점 | 남은 세부를 모두 질문으로 만들면 질문이 많아집니다.<br>ADR-003에서 정한 방향("아키텍처부터는 초안을 보여 주고 승인받는 쪽")과도 멉니다. |
| 결과 | 조건 1과 3은 지킵니다.<br>질문이 많아서 조건 2는 일부만 지킵니다. |

### 안 다. 전부 쓰고 한 번에 확인받기

| 구분 | 내용 |
|---|---|
| 장점 | 가장 빠릅니다. |
| 단점 | 한 번에 볼 양이 많습니다.<br>혼자 끝까지 쓰다 보면 빈칸을 짐작으로 채우기 쉽습니다. |
| 결과 | 조건 1은 지킵니다.<br>조건 2는 지키지 못하고, 조건 3은 일부만 지킵니다. |

### 한눈에 비교

| | 안 가 | 안 나 | 안 다 |
|---|---|---|---|
| 조건 1. 정한 것은 다시 묻지 않음 | ○ | ○ | ○ |
| 조건 2. 한 번에 볼 양이 적음 | ○ 탭 하나씩 | △ 질문이 많음 | ✗ 전체를 한 번에 |
| 조건 3. 짐작으로 채우지 않음 | ○ | ○ | △ |

### 하나로 정해 두지 않음

세 안은 맞는 때가 다릅니다.

| 안 | 맞는 때 |
|---|---|
| 안 가. 탭마다 초안 | 큰 갈림길이 범위에서 정해졌고, 남은 것이 세부일 때 |
| 안 나. 질문지 먼저 | 자료끼리 다르거나 빈 곳이 많을 때 |
| 안 다. 전부 쓰고 한 번에 | 탭이 적고 내용이 단순할 때 |

ADR-002도 단계를 전체에 한 번 할지 탭마다 할지 에이전트에 정해 두지 않고, 그때그때 대화로 정하기로 했습니다.  
그래서 하나로 정해 두지 않고, 뼈대를 확인받은 뒤 세 안을 추천과 함께 보여 주고 사람이 고르게 합니다.

- 어느 안이든 근거가 없는 칸은 질문 대기에 올립니다(에이전트 사이의 약속). 그래서 안 다의 조건 3도 이 약속으로 막습니다.
- 안 다를 고를 때는 한 번에 볼 양이 많다는 것(조건 2)을 알립니다.
- 범위와 자료를 보고 맞는 안을 추천합니다. 따로 맞는 안이 없으면 한 번에 볼 양이 가장 적은 안 가를 추천합니다.

이번 프로젝트에서는 안 가(탭마다 초안)를 골랐습니다(2026-10-23).  
처음에는 안 가 하나로 정해 두려 했다가, 검토에서 때에 따라 고르게 바꿨습니다.

## 질문 4. 팀 검토는 어떻게 하나

ADR-002의 ② 요건 확정은 "요건을 정리한 사람이 먼저 보고, 팀 회의에서 팀원이 확인"합니다.  
팀원 가운데는 저장소를 직접 보지 않는 사람도 있어서, 범위 질문지는 노션에 올려 검토했습니다(2026-10-23).

### 안 ㄱ. 확인 대기가 되면 팀 검토용 사본을 올릴지 묻기

| 구분 | 내용 |
|---|---|
| 장점 | 팀이 익숙한 곳(노션 등)에서 봅니다.<br>매번 따로 말하지 않아도 에이전트가 묻습니다. |
| 단점 | 검토하는 동안 원본이 둘이 됩니다.<br>그래서 검토 중에는 사본에서만 의견을 받고 파일은 고치지 않으며, 검토가 끝나면 의견을 파일로 옮깁니다. 범위 검토 때와 같은 방식입니다. |

### 안 ㄴ. 설명서에 넣지 않기

| 구분 | 내용 |
|---|---|
| 장점 | 설명서가 단순합니다. |
| 단점 | 사람이 매번 따로 요청해야 합니다.<br>사본을 올리고 의견을 옮기는 방법이 그때그때 달라집니다. |

안 ㄱ으로 정했습니다.

## 결정

질문 1은 안 3(탭마다 파일), 질문 2는 안 A(업무 말로 "무엇을"까지), 질문 3은 하나로 정해 두지 않고 구동할 때 고르게 했습니다(이번 프로젝트는 안 가, 탭마다 초안). 질문 4는 안 ㄱ(팀 검토용 사본을 올릴지 묻기)으로 정했습니다.

아래는 ADR-003의 「에이전트 ADR에 쓸 것」 8가지 순서입니다.

**1. 하는 일**

- 하는 일: 확정된 범위를 읽고, 화면 탭별로 요건을 업무 말로 씁니다. 탭 목록도 여기서 정합니다.
- 하지 않는 일: `scope.md`에서 정한 답을 다시 정하지 않습니다.  
  화면 동작, 화면 모양, 데이터와 시스템 연결은 쓰지 않고 넘길 단계와 함께 「다른 단계로 넘길 것」에 적습니다.

요건과 설계의 경계는 「요약」의 표를 따르고, 애매하면 두 가지로 판단합니다.

- 비개발자가 회의에서 "맞다, 아니다"를 말할 수 있으면 요건입니다.
- 같은 요건을 화면 조작이나 데이터로 여러 방법으로 만들 수 있다면, 그 방법은 뒤 단계에서 정합니다.

"장애 목록" 탭을 예로 들면 이렇습니다. 예시는 설명을 위해 지어낸 것입니다.

| 무엇 | 예 | 어느 단계 |
|---|---|---|
| 누가 무엇을 할 수 있어야 하나 | IT 담당자는 처리하지 않은 장애를 급한 것부터 볼 수 있어야 한다. | 요건정리 |
| 업무 규칙 | 급한 정도는 등급으로 정하고, 같은 등급이면 먼저 들어온 것이 먼저다. | 요건정리 |
| 함께 쓰는 정보 | 장애 정보에는 제목, 등급, 신고 시각이 들어 있다. | 아키텍처 |
| 화면 모양 | 장애 목록은 카드 모양이고, 등급은 색으로 구분한다. | 디자인 |
| 화면 동작 | 등급으로 거를 수 있다. 카드를 누르면 상세가 열린다. | 스펙 |

AI가 하는 일도 같습니다.  
AI가 무엇을, 어떤 기준으로 판단하나는 요건이고, AI를 어떻게 만드나(에이전트 구성, 모델)는 아키텍처입니다.

**2. 읽는 것**

- `docs/requirements/scope.md`를 읽습니다. 상태가 확정일 때만 시작합니다.
- 「다른 단계로 넘길 것」 가운데 넘길 단계가 요건정리인 것이 이번에 정할 것입니다.  
  하나도 빠짐없이 요건, 질문 대기, 다른 단계로 넘길 것 가운데 한 곳으로 옮깁니다.
- 「미룬 것과 뺀 것」에 있는 것은 요건에 넣지 않습니다.
- `scope.md`의 참고 자료 목록에 있는 자료를 탭을 쓸 때 필요한 만큼 읽습니다.
- 우리 프로젝트에서 무엇을 읽는지는 설명서에 적지 않습니다. 설명서는 다른 일에도 쓸 수 있게 둡니다.

**3. 남기는 것**

- `docs/requirements/requirements.md`: 상태와 확인, 팀 검토 사본 위치, 진행 방식, 읽은 것(`scope.md`의 확정 날짜와 읽은 때의 커밋), 사용자, 탭 목록과 탭별 상태, 0. 공통 요건, 정한 것, 질문 대기, 다른 단계로 넘길 것
- `docs/requirements/tabs/<두 자리 번호>-<탭 이름>.md`: 상태와 확인, 팀 검토 사본 위치, 이 탭은 누가 무엇을 하려고 쓰나, 요건, 정한 것, 질문 대기
- 요건 표의 칸은 번호, 요건, 업무 규칙, 근거, 우선입니다.  
  - 요건: "(누가)는 (무엇을) 할 수 있어야 한다." AI나 시스템이 하는 일은 "(무엇이 되면) (무엇을) 한다."
  - 업무 규칙: 조건과 수치입니다. 수치에는 출처를 적습니다(저장소 규칙).
  - 근거: `scope.md`의 대목, 참고 자료와 대목, 또는 「정한 것」의 번호입니다.
  - 우선: 꼭, 나중 가운데 하나입니다.
- 요건정리에서 물어서 정한 것은 「정한 것」에 고른 답, 고르지 않은 안, 이유와 함께 남깁니다. `scope.md`와 같은 이유로, 나중에 "왜 이렇게 했지?"를 찾을 수 있게 하기 위해서입니다.
- 「다른 단계로 넘길 것」은 `requirements.md` 한곳에 모읍니다. 아키텍처와 디자인이 한곳만 보면 되게 하기 위해서입니다.
- 파일 이름과 번호
  - 탭 파일 이름은 두 자리 번호와 한글 탭 이름을 띄어쓰기 없이 붙여 짓습니다(예: `01-상담등록.md`).  
    비개발자와 탭별로 회의하는 문서라서, 파일 목록에서도 탭 이름이 그대로 보이게 하기 위해서입니다.  
    띄어쓰기를 빼는 것은 링크와 명령에서 파일 이름이 끊기지 않게 하기 위해서입니다.  
    git은 한글 파일 이름을 `\354\203...`처럼 바꿔 보여 줄 수 있습니다. 그럴 때는 `git config core.quotepath false`로 한글 그대로 보이게 합니다.  
    처음에는 영어 이름(예: `01-intake.md`)으로 정했다가, 2026-10-23 검토에서 한글로 바꿨습니다.
  - 탭 이름이 바뀌면 파일 이름도 바꾸고, 탭 목록의 링크도 맞춥니다.
  - 탭 번호는 탭 목록의 번호입니다. 탭을 빼도 그 번호는 다시 쓰지 않습니다.
  - 요건 번호는 `<탭 번호>-<두 자리 순번>`입니다(예: `1-03`). 공통 요건은 `0-01`처럼 0을 씁니다. 요건을 빼도 번호는 다시 매기지 않습니다.  
    스펙, 구현 계획, 테스트 항목이 요건 번호로 거슬러 올라올 수 있게 하기 위해서입니다.
- 양식은 `.claude/skills/sdd-analyst/`에 둡니다. `template.md`는 `requirements.md`, `template-tab.md`는 탭 파일의 양식입니다.  
  ADR-003은 양식 파일을 `template.md` 하나로 적었지만, 남기는 파일이 두 종류라서 양식도 둘을 둡니다.

**4. 대화 순서**

- 위 「요약」의 흐름을 따릅니다.
- `scope.md`가 확정이 아니면 시작하지 않고, 인터뷰(`/sdd-interviewer`)를 안내합니다.
- `requirements.md`가 이미 있으면 파일마다 상태를 보고 나눕니다.
  - 작성 중: 이어서 할지 묻고, 그 파일의 질문 대기부터 합니다.
  - 확인 대기: 확정할지, 고칠 곳이 있는지 묻습니다. 팀 검토 사본이 있으면 검토가 끝났는지 묻습니다.
  - 확정: 무엇을 고칠지 묻고, 고치면 확인 대기로 되돌립니다. 아키텍처나 디자인이 되돌려 보낸 경우도 여기로 옵니다.
- 새로 시작하면 하는 일과 하지 않는 일을 두세 줄로 알립니다.
- 뼈대: 사용자, 탭 목록, 공통 요건의 제목, `scope.md`에서 넘겨받은 것을 어디서 다룰지를 보여 주고 확인받습니다.  
  탭 목록에 근거가 없으면 안을 둘 이상 놓고 추천과 근거를 붙여 묻습니다.  
  확인받으면 `requirements.md`를 만듭니다(작성 중).
- 진행 방식: 뼈대를 확인받으면 세 안(탭마다 초안, 질문지 먼저, 전부 쓰고 한 번에)을 맞는 때와 추천을 붙여 보여 주고 고르게 합니다.  
  고른 방식은 `requirements.md` 맨 위에 적어서, 이어서 할 때도 같은 방식으로 합니다.
- 초안: 어느 방식이든 공통 요건부터 씁니다. 탭 순서는 사람에게 묻고, 추천은 "꼭" 요건이 많은 탭부터입니다.  
  초안은 쓰자마자 파일에 남깁니다(작성 중). 대화가 끊기거나 길어져서 앞 내용이 줄어도 남게 하기 위해서입니다(ADR-004와 같은 이유).
- 질문은 질문 도구로 한 번에 4개까지, 추천 답을 첫 선택지로 둡니다. 사람이 원하면 표로 한 번에 보여 줍니다.
- 답하다가 `scope.md`에서 정한 답과 어긋나면, `scope.md`를 고치지 않고 무엇이 왜 걸리는지 말한 뒤 인터뷰로 되돌려 보냅니다.  
  걸린 요건은 질문 대기에 "인터뷰로 되돌림"으로 남깁니다.

범위가 바뀌었을 때(에이전트 사이의 약속, 2026-10-23에 더함)

- 부를 때 `requirements.md` 「읽은 것」의 커밋과 지금 `scope.md`의 마지막 커밋을 비교합니다.  
  다르면 범위가 바뀐 것이므로, 다른 일보다 먼저 이것부터 합니다.  
  처음에는 확정 날짜를 비교했다가, 2026-10-24 약속을 바꾸면서(ADR-006) 커밋 비교로 바꿨습니다.
- 읽은 때의 커밋과 지금 `scope.md`를 비교(git diff)해 바뀐 질문과 답을 찾습니다. 커밋을 찾을 수 없으면 사람에게 바뀐 곳을 묻습니다.
- 바뀐 것마다 걸리는 곳을 찾습니다. 요건마다 「근거」 칸에 `scope.md`의 대목을 적어 두므로, 그 대목을 가리키는 요건을 모든 파일에서 찾습니다. 사용자, 탭 목록, 공통 요건도 봅니다.
- 바뀐 것, 걸리는 요건(번호와 파일), 고칠 안을 표로 보여 주고 확인받은 대로 고칩니다.
- 고친 파일이 확인 대기나 확정이었으면 확인 대기로 되돌리고 다시 확인받습니다. 걸리지 않는 파일은 그대로 둡니다.
- 「정한 것」에 "범위 변경으로 고침"과 바뀐 `scope.md` 대목, 날짜를 남깁니다.
- 끝나면 「읽은 것」의 확정 날짜와 커밋을 새것으로 바꿉니다.

**5. 사람 확인**

확인은 파일마다 두 번입니다(ADR-002 ②).

| 누가 | 상태 | 확인 칸 |
|---|---|---|
| 정리한 사람이 확인 | 작성 중 → 확인 대기 | 정리한 사람 (이름, 날짜) |
| 팀이 확인 | 확인 대기 → 확정 | 팀 (확인한 사람, 날짜) |

- 질문 대기가 남아 있으면 확인 대기로 바꾸기 전에 묻습니다. 지금 정할 수 없으면 사람에게 미룰지 묻고, 「정한 것」에 "미룸"과 이유를 적습니다.
- 확인 대기로 바꿀 때 팀 검토용 사본을 올릴지 묻습니다.  
  올리면 파일 맨 위에 사본 위치를 적고, 검토하는 동안에는 파일을 고치지 않습니다.  
  사본에는 요건 표와 질문 대기에 「의견」 칸을 더합니다. 노션 질문지의 「확인」 체크처럼 뜻이 갈리는 칸은 두지 않습니다.  
  검토가 끝나면 의견을 파일로 옮기고, 바뀐 곳을 보여 줍니다.
- 확정은 사람이 확인했다고 말할 때만 합니다. 누가 확인했는지 말하지 않았으면 묻습니다.
- 탭 파일의 상태가 바뀌면 `requirements.md` 탭 목록의 상태도 같이 바꿉니다.

**6. 지킬 것**

- `scope.md`에서 정한 답을 다시 정하지 않습니다. 고쳐야 하면 인터뷰로 되돌려 보냅니다.
- 근거가 없는 규칙과 수치는 짐작으로 채우지 않고 질문 대기에 올립니다.
- 실제 고객 정보, 실제 장애 사례, 사내 시스템 이름은 요건 문서에 넣지 않습니다(저장소 규칙).  
  참고 자료에서 옮길 때와 팀 검토 사본에서 의견을 옮길 때 모두 일반 이름으로 바꿉니다.

**7. 다음 단계로 넘기기**

- `requirements.md`와 탭 파일이 확정되면, 다음은 아키텍처(`/sdd-architect`)와 디자인(`/sdd-designer`)이라고 알려 줍니다. 둘은 나란히 할 수 있습니다.  
  아직 만들지 않은 에이전트면 그렇다고 알립니다.
- 아키텍처와 디자인은 작성 중인 `requirements.md`와 탭 파일로도 초안을 쓸 수 있고, 확정은 요건 파일이 모두 확정된 뒤에 합니다(바뀐 약속, ADR-006).
- 그래서 확정되지 않은 파일이 남았으면 그 목록을 함께 알려 줍니다.  
  처음에는 "확정된 파일만 읽고, 남은 탭이 있으면 시작할지 사람이 정한다"였다가 2026-10-24에 바꿨습니다.

**8. 시험 장면**

가상 자료와 가상의 확정 `scope.md`는 `_raw/test/`에 두고 git에 올리지 않습니다.  
`scope.md`가 확정되기 전에 시험할 때는 작업 공간을 나눠서(git worktree 등) 실제 `docs/requirements/`를 건드리지 않습니다.

| # | 장면 | 통과 |
|---|---|---|
| 1 | `scope.md`가 확정이 아닐 때 부릅니다. | 시작하지 않고, 이유와 인터뷰(`/sdd-interviewer`)를 안내합니다.<br>파일을 만들지 않습니다. |
| 2 | 확정된 `scope.md`로 부릅니다. | 처음 보여 주는 것이 사용자, 탭 목록, 공통 요건의 뼈대입니다. 확인받기 전에는 파일을 만들지 않습니다.<br>`scope.md`에서 요건정리로 넘긴 것이 하나도 빠짐없이 요건, 질문 대기, 다른 단계로 넘길 것 가운데 한 곳에 있습니다.<br>뼈대를 확인받은 뒤 진행 방식을 세 안과 추천으로 묻고, 고른 방식이 `requirements.md` 맨 위에 적힙니다. |
| 3 | 탭 하나의 초안을 받습니다. | 요건이 업무 말로 쓰였고, 화면 동작, 화면 모양, 데이터 구조가 없습니다.<br>모든 요건에 근거가 있습니다. |
| 4 | 자료에 근거가 없는 수치가 필요한 요건이 있습니다. | 짐작한 수치가 업무 규칙에 없고, 질문 대기에 올라 있습니다.<br>추천 답은 근거가 있을 때만 있습니다. |
| 5 | 답하다가 `scope.md`에서 정한 답을 바꾸자고 하고, 화면 모양 이야기도 꺼냅니다. | `scope.md`를 고치지 않고 인터뷰로 되돌려 보내야 한다고 알립니다.<br>화면 모양은 넘길 단계(디자인)와 함께 「다른 단계로 넘길 것」에 적힙니다. |
| 6 | 탭 하나를 정리한 사람이 확인하고, 이어서 팀이 확인했다고 말합니다. | 그 탭 파일만 확인 대기를 거쳐 확정으로 바뀝니다. 확인 대기로 바꿀 때 팀 검토 사본을 올릴지 묻습니다.<br>확인 칸 두 개가 채워지고, `requirements.md` 탭 목록의 상태도 같습니다.<br>마지막에 다음 단계를 알려 줍니다. |
| 7 | 가상의 사내 시스템 이름과 고객 정보가 든 자료나 사본 의견을 줍니다. | 요건 문서에 그 이름과 정보가 없고, 일반 이름으로 바뀌어 있습니다. |
| 8 | 요건을 쓴 뒤 `scope.md`의 답 하나를 바꿔 다시 확정하고 부릅니다. | 다른 일보다 먼저 바뀐 곳과 걸리는 요건을 표로 보여 줍니다.<br>걸리는 파일만 확인 대기로 돌아가고, 걸리지 않는 파일은 그대로입니다.<br>「읽은 것」의 확정 날짜와 커밋이 새것으로 바뀝니다. |

## 주의할 점

- 이 ADR은 ADR-002 「주의할 점」의 "탭별 파일 이름"에 답합니다.  
  ADR-002의 「남기는 것」 표는 `requirements.md` 하나로 적혀 있으므로, 이 ADR을 채택할 때 ADR-002에 이 ADR을 가리키는 한 줄을 더합니다.
- 스펙(`spec.md`)도 탭마다 쓰게 되면, 스펙 에이전트를 만들 때 같은 방식(탭마다 파일)을 쓸지 정합니다.
- 팀 검토 사본은 노션에 올릴 때가 많겠지만, 설명서에는 "팀 검토용 사본"으로만 적습니다. 어디에 올릴지는 구동할 때 사람이 정합니다.
