# ADR-009 스펙·구현 계획 에이전트 없이 구현 계획 한 장으로 먼저 만들기

- 상태: 채택 (2026-10-25)
- 날짜: 2026-10-25

> 적용 범위: 「스펙·구현 계획·실행형 에이전트를 먼저 만들지 않는다」는 지금도 그대로입니다([SDD 한눈에 보기](../guide/sdd.md)의 「만들었나」).  
> 「구현 계획 한 장을 쓰고 Claude Code가 앱을 바로 만든다」는 부분은 시연용 구현에 적용한 것입니다. 제출 구현(VocAi)은 개발 담당이 따로 개발했습니다([ADR-010](ADR-010-submission-implementation.md)).  
> 구현 뒤 타입 검사·디자인 규칙 검사·빌드 같은 검증도 시연용 구현에서 쓴 것이고, 이 저장소에는 그 도구가 없습니다.

## 요약

이번 제출(사전 제출 10/30 24:00)까지는 스펙 에이전트, 구현 계획 에이전트, 실행형 에이전트(백엔드, 프론트, 코드 리뷰, QA)를 먼저 만들지 않습니다.  
확정한 요건·아키텍처·디자인을 바탕으로 구현 계획 한 장(`docs/plan/plan.md`)을 쓰고, Claude Code가 그 계획대로 앱을 바로 만듭니다.  
스펙 단계는 이번에 건너뛰고, 스펙으로 넘겼던 화면 동작은 구현하면서 정해 `plan.md` 「구현하며 정한 것」에 남깁니다.

10/26(월) 팀 데모에서 받은 피드백으로 고칠 것이 나오면, ADR-002의 순서대로 인터뷰부터 차례로 고칩니다.  
시간이 남으면 만들지 못한 에이전트를 만들고, 건너뛴 스펙은 그때 「구현하며 정한 것」을 근거로 거꾸로 채웁니다.

## 배경

ADR-002는 디자인 다음에 스펙(⑤ 스펙 승인) → 구현 계획(⑥ 계획 승인) → 구현으로 가는 흐름을 정했습니다.  
10/25 기준으로 범위·요건·아키텍처·디자인은 확정됐지만, 다음 단계를 맡을 스펙·구현 계획 에이전트와 실행형 에이전트 4개는 아직 하나도 없습니다(`.claude/agents/` 비어 있음).

남은 시간은 짧습니다.

- 사전 제출 마감: 10/30(금) 24:00 (노션 「04. 본선 진출 안내」, 10/24 공지)
- 팀 목표 최종본: 10/28 (노션 질문지 5번 의견, 개발 담당)
- 10/26(월): 팀원과 데모를 보며 이야기하기로 함 (10/25)

## 지켜야 할 조건

1. 10/26 팀 데모에서 핵심 흐름(상담 등록 → AI 판단 → 알림·승인 → 처리)이 실제로 돌아야 합니다.
2. 확정한 요건·아키텍처·디자인을 다시 정하지 않습니다.
3. 건너뛴 단계에서 정했어야 할 것을 잃어버리지 않고 남깁니다.
4. 나중에 원래 흐름(ADR-002)으로 돌아갈 수 있습니다.

## 검토한 안

### 안 1. 에이전트를 먼저 만들고 흐름대로 가기

스펙·구현 계획 에이전트를 만들고, 탭마다 스펙 → 계획 → 구현으로 갑니다.

| 구분 | 내용 |
|---|---|
| 장점 | ADR-002 흐름과 사람이 확인하는 곳 7곳을 그대로 지킵니다. |
| 단점 | 에이전트를 만들고 시험하는 데 반나절에서 하루가 더 듭니다(인터뷰~디자인 에이전트를 만들 때 하나에 반나절 안팎). 10/26 데모에 앱이 없을 수 있습니다. |

### 안 2. 구현 계획 한 장을 쓰고 바로 구현하기 (고른 안)

아키텍처와 화면 규칙의 「다른 단계로 넘길 것」에서 구현 계획으로 넘긴 것을 모아 `plan.md` 한 장으로 답하고, 그 계획대로 구현합니다.

| 구분 | 내용 |
|---|---|
| 장점 | 데모 전에 앱을 만들 시간이 남습니다. 작은 기술 선택과 만드는 순서는 계획에 남아 사람이 봅니다. |
| 단점 | 스펙(⑤)을 건너뛰어 화면 동작을 사람이 미리 확인하지 못합니다. 구현하면서 정한 것을 따로 잘 남겨야 합니다. |

### 안 3. 계획 없이 바로 구현하기

| 구분 | 내용 |
|---|---|
| 장점 | 가장 빠릅니다. |
| 단점 | 작은 기술 선택과 넘겨받은 것들이 코드 속에만 남습니다. 팀이 무엇을 어떻게 만들었는지 알기 어렵습니다(ADR-002 「배경」의 문제). |

## 결정

안 2로 정했습니다(2026-10-25: "말씀하신 안으로 쭉 이어서 진행").

- 구현 계획: `docs/plan/plan.md` 한 장. 상태는 확인 대기로 두고, 구현은 먼저 시작합니다. 계획 승인(⑥)은 데모 뒤 사람이 계획과 앱을 함께 보고 합니다.
- 스펙(⑤): 이번에는 건너뜁니다. 스펙으로 넘겼던 화면 동작(누르면 어떻게 되나, 화면 갱신 간격 등)은 구현하면서 정하고 `plan.md` 「구현하며 정한 것」에 적습니다.
- 구현: 실행형 에이전트 없이 Claude Code가 직접 만듭니다. 만든 뒤 타입 검사, 디자인 규칙 검사, 빌드, 화면 확인을 합니다.
- 앱 코드가 어디에 있는지는 [ADR-010](ADR-010-submission-implementation.md)을 봅니다.

## 이후

- 10/26 팀 피드백으로 고칠 것이 나오면, 범위에 걸리면 인터뷰(`/sdd-interviewer`)부터, 요건에 걸리면 요건정리부터 차례로 고칩니다(약속: `.claude/rules/sdd.md`). 앱은 고친 문서를 따라 고칩니다.
- 시간이 남으면 스펙·구현 계획·실행형 에이전트를 만듭니다. 그때 이번에 만든 화면과 「구현하며 정한 것」을 근거로 스펙을 채우고, 이 ADR의 상태를 다시 봅니다.
