# ADR-006 아키텍처 에이전트

- 상태: 채택
- 날짜: 2026-10-24

## 요약

아키텍처는 요건(`requirements.md`와 탭 파일)을 읽고, 여러 탭이 같이 쓰는 것을 한곳에서 정하는 단계입니다.  
시스템이 어떤 덩어리로 나뉘고 어떻게 이어지는지, 함께 쓰는 정보, 제품 AI가 판단하는 흐름, 큰 기술 선택을 씁니다.  
기술 선택처럼 갈림길이 있는 것은 안을 놓고 사람이 고르고, 나머지는 장마다 초안을 보여 주고 확인받습니다.  
결과는 `docs/architecture/architecture.md` 한 파일에 남기고, 탭마다 걸리는 곳은 「탭별로 보기」 장에 모읍니다.

요건이 확정되기 전에도 초안은 씁니다. 확정(③ 아키텍처 승인)은 읽은 요건이 모두 확정된 뒤에만 합니다.  
요건 파일이 바뀌면 읽은 때의 커밋과 비교해, 바뀐 탭에 걸리는 곳만 고칩니다.  
이렇게 하려고 에이전트 사이의 약속도 함께 바꿨습니다(「질문 3」).

```
requirements.md와 탭 파일을 읽는다 (작성 중이어도 읽음, 파일마다 상태와 커밋을 남김)
  ↓
뼈대를 보여 주고 확인받는다 (장 목록, 갈림길 목록, 넘겨받은 것을 어디서 다룰지) → architecture.md를 만든다 (작성 중)
  ↓
갈림길을 안과 추천으로 묻는다 (기술 선택, 제품 AI 구성 등)
  ↓
장마다 초안을 쓰고 보여 준다 → 고칠 곳과 질문의 답을 받는다
  ↓            ↖ 요건 파일이 바뀌면: 커밋을 비교해 바뀐 요건 번호를 찾고, 걸리는 곳만 고친다
질문 대기가 없으면 확인 대기 → 팀 검토용 사본을 올릴지 묻는다
  ↓
읽은 요건이 모두 확정되고 사람이 승인하면 확정 → 스펙으로 (디자인 승인도 끝나야 함)
```

```
docs/architecture/
└── architecture.md     상태: 작성 중 → 확인 대기 → 확정 (파일 전체에 하나)
    ├── 읽은 것              요건 파일마다 읽은 때의 상태와 커밋
    ├── 1. 한눈에 보기       덩어리와 연결 (그림)
    ├── 2. 함께 쓰는 정보    정보마다 항목과 상태 값, 근거 요건 번호
    ├── 3. AI 판단 흐름      제품 AI 구성, 단계, 사람이 끼어드는 곳
    ├── 4. 기술 선택         큰 선택만. 고른 것, 고르지 않은 것, 이유
    ├── 5. 실패와 예외       AI 호출 실패, 시간 초과 등
    ├── 6. 비밀과 시험 자료  키 보관, 가상 자료
    ├── 7. 탭별로 보기       탭마다 쓰는 정보, 흐름에서 맡는 단계, 근거 요건 번호
    ├── 정한 것
    ├── 질문 대기
    └── 다른 단계로 넘길 것
```

아키텍처와 앞뒤 단계의 경계는 이렇게 정했습니다.

| 아키텍처가 쓰는 것 | 쓰지 않는 것 (정한 단계 또는 넘길 단계) |
|---|---|
| 시스템의 덩어리와 연결 (화면, 서버, AI 판단, 저장소, 알림) | 누가 무엇을 할 수 있어야 하나, 업무 규칙과 수치 (요건정리) |
| 여러 탭이 같이 쓰는 정보와 그 항목, 상태 값 | 화면 모양, 배치, 색 (디자인) |
| 제품 AI 구성과 판단 흐름, 사람 승인이 끼어드는 곳 | 탭의 버튼과 화면 이동, 화면이 서버에 무엇을 요청하나 (스펙) |
| 큰 기술 선택 (LLM, 임베딩, DB, LangGraph를 쓸지, 앱 언어와 프레임워크) | 작은 기술 선택 (라이브러리, 버전, 화면 부품 묶음), 파일, 표의 칸 형식, 코드 (구현 계획) |
| 비슷함을 재는 방법처럼 요건이 "아키텍처에서 정한다"고 넘긴 것 | |

여러 탭이 같이 쓰거나, 한번 정하면 모든 탭의 스펙이 따라야 하는 것이면 아키텍처입니다.  
탭 하나 안에서만 쓰이는 것이면 스펙에서 정합니다.

- 묻기 전에 요건, 범위, 인터뷰 검토 사본, 참고 자료에서 관련 대목을 찾아 질문에 붙입니다(2026-10-24 첫 구동 뒤 더함).
- 시험 장면은 11개이고, 「결정」 8번에 있습니다.

자세한 내용은 아래 「결정」에 있습니다.

## 배경

ADR-002에서 정한 개발 에이전트 10개 가운데 세 번째인 아키텍처 에이전트(`sdd-architect`)를 만듭니다.  
ADR-003의 만드는 순서에서 첫 단계(에이전트 ADR 쓰기)에 해당합니다.

ADR-002는 아키텍처를 스펙보다 먼저 두었습니다.  
여러 탭이 같이 쓰는 것(예: 장애 정보)을 한곳에서 먼저 정해야 탭 스펙끼리 어긋나지 않기 때문입니다.  
디자인과는 나란히 진행하고, 스펙은 둘 다 승인된 뒤에 씁니다.

앞 단계에서 아키텍처로 넘겨 둔 것이 있습니다.

- 범위(`scope.md`)의 「다른 단계로 넘길 것」: 제품 에이전트 구성, LangGraph를 쓸지, LLM·임베딩·DB, 성능이 보장되는 LLM을 써야 하는지와 발표 때 상용 API 연동을 보여 줄지, AI 호출이 실패해도 멈추지 않게 하는 방법
- 요건(`requirements.md`)의 「다른 단계로 넘길 것」: 과거 오탐과 얼마나 비슷해야 비슷하다고 보나(비슷함을 재는 방법과 기준값)

이 단계에서 함께 정할 것이 세 가지 있습니다.

- ADR-002는 구현 계획이 "기술 스택 ADR"을 읽는다고 적었지만, 그 ADR을 누가 언제 쓰는지는 정하지 않았습니다.
- 요건은 탭 7개 초안을 모두 썼지만 아직 모두 작성 중이고, 팀이 검토하고 있습니다(2026-10-24).  
  마감은 10/28 최종본입니다(노션 질문지 5번, 팀이 날짜 확인 중).  
  그런데 약속은 "다음 단계는 확정된 문서만 읽고 시작한다"여서, 요건이 모두 확정될 때까지 아키텍처를 시작할 수 없습니다.
- 아키텍처 문서는 기술 용어가 많아서, "사람이 읽는 문서는 업무 말로 쓴다"는 약속을 어떻게 지킬지 정해야 합니다.

## 정할 것

ADR-003의 「에이전트 ADR에 쓸 것」 8가지를 정합니다.

| 항목 | 무엇을 정하나 | 지금 아는 것 |
|---|---|---|
| 1. 하는 일 | 아키텍처가 쓰는 것과 쓰지 않는 것 | 여러 탭이 같이 쓰는 것을 한곳에서 정함 (ADR-002)<br>기술 스택을 어디서 정하나는 **질문 1** |
| 2. 읽는 것 | 무엇을 읽고 시작하나 | `requirements.md`와 탭 파일 (ADR-005)<br>확정 전에도 읽을지는 **질문 3** |
| 3. 남기는 것 | 아키텍처 문서의 모양 | `docs/architecture/architecture.md` (ADR-002)<br>나눌지는 **질문 2** |
| 4. 대화 순서 | 어떻게 묻고 쓰나 | 초안을 보여 주고 승인받는 쪽 (ADR-003)<br>자세히는 **질문 4** |
| 5. 사람 확인 | 누가 확정하나 | 승인해야 스펙을 씀 (ADR-002 ③) |
| 6. 지킬 것 | 하면 안 되는 것 | 저장소 규칙, 에이전트 사이의 약속 |
| 7. 다음 단계로 넘기기 | 스펙과 구현 계획이 무엇을 이어받나 | 확정된 `architecture.md`, 기술 스택 ADR |
| 8. 시험 장면 | 3개 이상, 각각 무엇이 나오면 통과인지 | 아직 정하지 않음 |

## 질문 1. 기술 스택은 어디서 정하나

### 지켜야 할 조건

1. 범위가 아키텍처로 넘긴 기술 선택(LLM, 임베딩, DB, LangGraph)을 빠짐없이 정합니다.
2. 모든 탭이 같은 기술 위에서 만들어집니다.
3. 구현 계획이 읽을 "기술 스택 ADR"이 생깁니다(ADR-002). 구조나 방식을 새로 정하면 ADR을 남깁니다(CLAUDE.md).
4. 마감에 맞게 일찍 정해져서, 앱 코드를 일찍 시작할 수 있습니다.

### 안 1. 큰 선택은 아키텍처, 작은 선택은 구현 계획

LLM, 임베딩, DB, LangGraph를 쓸지, 앱 언어와 프레임워크는 아키텍처에서 고릅니다.  
라이브러리, 버전, 화면 부품 묶음은 구현 계획에서 고릅니다.  
스펙은 기술을 정하지 않고, 아키텍처가 고른 기술 위에서 동작만 정합니다.

| 구분 | 내용 |
|---|---|
| 장점 | 흐름과 기술을 함께 봅니다.<br>예를 들어 관리자 승인은 LangGraph를 쓰면 "흐름을 멈췄다가 승인되면 이어 가기"로, 쓰지 않으면 "승인 목록에 넣고 승인되면 다음 처리"로 만듭니다. 비슷한 오탐 찾기도 임베딩을 쓰는지에 따라 흐름이 달라집니다.<br>한 번 정하면 모든 탭이 따릅니다. |
| 단점 | `architecture.md`와 기술 스택 ADR 두 곳에 적힙니다.<br>그래서 원본은 `architecture.md` 「4. 기술 선택」으로 두고, ADR에는 고른 것과 이유만 쓰고 원본을 가리킵니다. 기술 선택을 고치면 둘을 함께 고칩니다. |
| 결과 | 네 조건을 모두 지킵니다. |

### 안 2. 스펙에서 정하기

탭의 동작을 정하면서 필요한 기술을 그때 고릅니다.

| 구분 | 내용 |
|---|---|
| 장점 | 동작을 정할 때 필요한 만큼만 고릅니다. |
| 단점 | 스펙은 탭 하나의 동작을 정하는 단계라서, 첫 탭의 스펙이 전체 기술을 정하거나 탭마다 기술이 달라질 수 있습니다.<br>아키텍처의 흐름을 기술 없이 승인했다가 스펙에서 다시 바꾸게 될 수 있습니다.<br>스펙은 아키텍처와 디자인이 승인된 뒤라서 기술이 늦게 정해집니다.<br>`scope.md`가 기술 선택을 아키텍처로 넘겨 두었으므로, 인터뷰에서 `scope.md`를 고쳐야 합니다. |
| 결과 | 조건 3은 지킵니다.<br>조건 1은 다른 곳에서, 조건 2는 일부만 지키고, 조건 4는 지키지 못합니다. |

### 안 3. 아키텍처 전에 따로 정하기

기술 스택 ADR을 먼저 쓰고, 아키텍처는 그것을 읽고 시작합니다.

| 구분 | 내용 |
|---|---|
| 장점 | 가장 일찍 정해집니다.<br>아키텍처가 할 일이 줄어듭니다. |
| 단점 | 흐름을 보기 전에 기술을 고르게 됩니다. LangGraph를 쓸지는 관리자 승인 흐름과 이어져 있습니다(범위 질문지 8번 의견).<br>범위가 아키텍처로 넘긴 것을 다른 곳에서 정하게 됩니다. |
| 결과 | 조건 2, 3, 4는 지킵니다.<br>조건 1은 아키텍처가 아닌 곳에서 지킵니다. |

## 질문 2. 아키텍처 문서를 어떤 모양으로 두나

### 지켜야 할 조건

1. 사람이 한 번에 승인할 수 있습니다(ADR-002 ③은 한 번).
2. 스펙과 구현 계획이 무엇을 읽어야 하는지 헷갈리지 않습니다.
3. 탭 하나의 요건이 바뀌었을 때, 그 탭에 걸리는 곳을 바로 찾습니다.
4. 스펙과 일이 겹치지 않습니다.

### 안 가. 한 파일

`architecture.md` 하나에 장을 나눠 씁니다. 상태도 하나입니다.  
요건이 바뀌면 장마다 달아 둔 근거 요건 번호로 걸리는 곳을 찾습니다.

| 구분 | 내용 |
|---|---|
| 장점 | ADR-002의 파일 표와 같습니다.<br>이 제품의 핵심은 탭을 가로지릅니다. 판단 흐름은 상담등록 → AI 판단 → 알림승인 → 장애목록으로 이어지고, 시험상담등록의 상담도 같은 흐름을 탑니다.<br>한 번에 보고 한 번에 승인하며, 탭끼리 어긋날 일이 없습니다. |
| 단점 | 어느 탭에 걸리는지 바로 보이지 않습니다. 요건 번호를 장마다 찾아야 합니다.<br>탭 하나의 요건만 바뀌어도 파일 전체가 확인 대기로 돌아갑니다. |
| 결과 | 조건 1, 2, 4는 지킵니다.<br>조건 3은 일부만 지킵니다. |

### 안 나. 한 파일 + 「탭별로 보기」 장

안 가에 장을 하나 더합니다.  
탭마다 쓰는 정보, 흐름에서 맡는 단계, 근거 요건 번호를 한 줄씩 모읍니다.

| 구분 | 내용 |
|---|---|
| 장점 | 안 가의 장점을 그대로 가집니다.<br>탭 3의 요건이 바뀌면 탭 3 줄에서 걸리는 정보와 단계를 바로 찾습니다.<br>요건의 탭 파일과 같은 번호로 줄을 두어서, 요건 회의 때 그 탭의 아키텍처도 같이 볼 수 있습니다. |
| 단점 | 본문과 이 장이 같은 내용을 두 번 가리킵니다. 본문을 고치면 이 장도 맞춰야 합니다.<br>탭 하나만 바뀌어도 파일 전체가 확인 대기로 돌아가는 것은 같습니다. 대신 바뀐 곳을 표로 보여 주므로 다시 볼 양은 그 탭만큼입니다. |
| 결과 | 네 조건을 모두 지킵니다. |

### 안 다. 공통 파일 + 탭마다 파일

`architecture.md`에 공통(덩어리, 함께 쓰는 정보, 흐름, 기술)을 두고, `tabs/`에 탭마다 파일을 따로 둡니다. 파일마다 상태가 있습니다.

### 약속을 바꿈

안 ㄷ은 아키텍처만의 사정이 아닙니다. 디자인과 스펙도 앞 단계가 확정되기 전에 시작할 일이 생깁니다.  
그래서 아키텍처 설명서에만 예외로 두지 않고, 에이전트 사이의 약속(`.claude/rules/sdd.md`)을 바꿉니다(2026-10-24).

| 지금까지 | 바꾼 뒤 |
|---|---|
| 다음 단계는 확정된 문서만 읽고 시작합니다. | 앞 단계 문서가 확정되기 전에도 초안은 쓸 수 있습니다. 내 문서의 확정은 읽은 앞 단계 문서가 모두 확정된 뒤에만 합니다. |
| 앞 단계 문서를 읽으면, 그 문서의 확정 날짜와 읽은 때의 커밋을 내 문서에 적습니다. | 앞 단계 문서를 읽으면, 그 문서의 상태(확정이면 확정 날짜)와 읽은 때의 커밋을 내 문서에 적습니다. |
| 앞 단계 문서가 그 뒤에 다시 확정되었으면, 읽었던 때와 비교해 바뀐 곳을 먼저 보여 주고, 걸리는 곳만 고칩니다. | 앞 단계 문서가 읽은 때의 커밋 뒤에 바뀌었으면, 비교해 바뀐 곳을 먼저 보여 주고, 걸리는 곳만 고칩니다. |

- 바뀐 것을 알아채는 기준을 "다시 확정됨"에서 "커밋이 다름"으로 바꿨습니다. 확정 전 문서는 확정 날짜가 없어서, 확정 날짜만으로는 바뀐 것을 알 수 없기 때문입니다.
- 약속은 "쓸 수 있다"입니다. 단계마다 더 엄격하게 둘 수 있습니다. 요건정리는 지금처럼 범위가 확정되어야 시작합니다(ADR-005). 범위는 모든 요건이 기대는 큰 갈림길이라서입니다.
- ADR-003의 약속 표와 ADR-005, 요건정리 설명서도 같은 날 맞췄습니다.

## 결정

질문 1은 안 1(큰 선택은 아키텍처, 작은 선택은 구현 계획), 질문 2는 안 나(한 파일 + 「탭별로 보기」), 질문 3은 안 ㄷ(초안은 작성 중인 요건으로, 확정은 요건이 모두 확정된 뒤에)과 약속 변경, 질문 4는 안 A(뼈대 → 갈림길 → 장마다 초안)로 정했습니다(2026-10-24).

아래는 ADR-003의 「에이전트 ADR에 쓸 것」 8가지 순서입니다.

**1. 하는 일**

- 하는 일: 요건을 읽고, 여러 탭이 같이 쓰는 것(덩어리와 연결, 함께 쓰는 정보, AI 판단 흐름, 큰 기술 선택, 실패와 예외)을 정합니다.
- 하지 않는 일: 요건에서 정한 답(업무 규칙, 수치, 등급 기준, 누가 무엇을 하나)을 다시 정하지 않습니다.  
  화면 모양, 탭의 화면 동작, 작은 기술 선택, 파일과 코드는 쓰지 않고 넘길 단계와 함께 「다른 단계로 넘길 것」에 적습니다.

경계는 「요약」의 표를 따르고, 애매하면 두 가지로 판단합니다.

- 여러 탭이 같이 쓰거나, 한번 정하면 모든 탭의 스펙이 따라야 하면 아키텍처입니다.
- 비개발자가 "맞다, 아니다"를 말할 수 있는 업무 규칙이면 요건입니다. 아키텍처에 필요한데 요건에 없으면 요건정리로 되돌려 보냅니다.

"장애 목록"을 예로 들면 이렇습니다. 예시는 설명을 위해 지어낸 것입니다.

| 무엇 | 예 | 어느 단계 |
|---|---|---|
| 업무 규칙 | 같은 등급이면 먼저 들어온 것이 먼저다. | 요건정리 |
| 함께 쓰는 정보 | 장애 정보에는 제목, 등급, 신고 시각, 처리 상태가 들어 있다. 처리 상태는 접수, 처리 중, 완료 가운데 하나다. | 아키텍처 |
| AI 판단 흐름 | 상담이 등록되면 장애인지 판별하고, 등급을 매기고, P1이면 바로 알림으로, P2·P3면 승인 목록으로 보낸다. | 아키텍처 |
| 큰 기술 선택 | 비슷한 과거 사례는 문장을 숫자로 바꿔(임베딩) 찾는다. | 아키텍처 |
| 화면 동작 | 등급으로 거를 수 있다. 화면은 서버에 장애 목록을 요청한다. | 스펙 |
| 작은 기술 선택, 표의 칸 형식 | 날짜는 이 라이브러리로 다룬다. 신고 시각은 날짜·시각 칸으로 둔다. | 구현 계획 |

**2. 읽는 것**

- `docs/requirements/requirements.md`와 `docs/requirements/tabs/`의 탭 파일을 상태와 상관없이 읽습니다(질문 3, 안 ㄷ).  
  `requirements.md`가 없으면 시작하지 않습니다.
- `requirements.md`의 「다른 단계로 넘길 것」 가운데 넘길 단계가 아키텍처인 것이 이번에 정할 것입니다.  
  하나도 빠짐없이 본문, 정한 것, 질문 대기, 다른 단계로 넘길 것 가운데 한 곳으로 옮깁니다.
- `scope.md`의 「다른 단계로 넘길 것」 가운데 아키텍처로 넘긴 것도 같이 옮깁니다.  
  처음에는 넘긴 것 표와 참고 자료 목록을 봅니다. 범위가 고쳐지면 요건정리가 걸리는 요건을 고치므로, 바뀐 것은 요건 파일로 봅니다.
- 묻거나 애매한 곳이 생기면, 묻기 전에 요건 → `scope.md` 전체 → 인터뷰 검토 사본(질문지와 팀 의견) → 참고 자료 순서로 관련 대목을 찾고, 찾은 것을 질문에 붙입니다(「묻기 전에 찾아보기」).  
  요건과 `scope.md`에서 정한 답은 다시 묻지 않고, 팀 의견과 참고 자료는 근거로 씁니다. 예전 설계는 그대로 따르지 않고 지금 요건과 다른 곳을 함께 적습니다.  
  처음에는 `scope.md`의 넘긴 것 표와 참고 자료 목록만 보게 했습니다. 2026-10-24 첫 구동에서 갈림길 ①을 물을 때 노션 plan과 v2 요건정의서에서 찾은 대목이 판단에 쓰여서, 묻기 전에 앞 단계 자료를 찾아보는 단계를 더했습니다.
- 디자인 문서는 읽지 않습니다. 둘은 나란히 진행하고, 어긋난 것은 스펙에서 찾아 되돌려 보냅니다(ADR-002).
- 우리 프로젝트에서 무엇을 읽는지는 설명서에 적지 않습니다. 설명서는 다른 일에도 쓸 수 있게 둡니다.

**3. 남기는 것**

- `docs/architecture/architecture.md` 한 파일입니다(질문 2, 안 나).  
  맨 위: 상태와 확인, 팀 검토 사본 위치  
  읽은 것: 요건 파일마다 읽은 때의 상태(확정이면 확정 날짜)와 읽은 때의 커밋, 아키텍처로 넘긴 것을 본 `scope.md`의 커밋, 참고한 자료와 본 대목, 읽은 날  
  본문: 1. 한눈에 보기, 2. 함께 쓰는 정보, 3. AI 판단 흐름, 4. 기술 선택, 5. 실패와 예외, 6. 비밀과 시험 자료, 7. 탭별로 보기  
  끝: 정한 것, 질문 대기, 다른 단계로 넘길 것
- 함께 쓰는 정보는 정보마다 표로 씁니다. 칸은 항목, 뜻, 값(상태 값처럼 정해진 값이 있으면), 근거입니다.  
  근거에는 요건 번호(예: `0-10`, `2-03`)를 적습니다. 요건이 바뀌었을 때 걸리는 곳을 그 번호로 찾기 위해서입니다.  
  칸 형식(글자, 숫자, 날짜)과 표 이름은 쓰지 않습니다. 구현 계획에서 정합니다.
- AI 판단 흐름은 그림과 단계 표로 씁니다. 단계마다 무엇을 받고 무엇을 넘기는지, 근거 요건 번호를 적습니다.
- 그림은 mermaid로 그립니다. 1장에는 덩어리와 연결, 전체 흐름을, 2장에는 정보끼리의 관계를 그림으로 둡니다.  
  처음에는 코드 블록 안의 글자 그림으로 정했다가, 2026-10-24 첫 구동에서 흐름을 그림으로 보고 싶다는 의견이 나와 mermaid로 바꿨습니다. 깃허브, 노션, 옵시디언에서 그림으로 보입니다.
- 기술 선택은 큰 선택만, 고른 것, 고르지 않은 안, 이유를 함께 남깁니다. 범위와 요건에서 넘겨받은 질문이 어디에 답했는지 알 수 있게 합니다.  
  작은 선택은 쓰지 않습니다. 정해야 할 것이 보이면 「다른 단계로 넘길 것」에 구현 계획으로 적습니다.
- 「7. 탭별로 보기」는 요건의 탭 목록과 같은 번호로 한 줄씩 씁니다. 칸은 탭, 쓰는 정보(2장의 정보 이름), 흐름에서 맡는 단계(3장의 단계), 근거 요건 번호입니다.  
  본문을 고치면 이 장도 같이 맞춥니다. 이 장에 본문에 없는 것을 새로 정하지 않습니다.
- 아키텍처에서 물어서 정한 것은 「정한 것」에 고른 답, 고르지 않은 안, 이유와 함께 남깁니다(ADR-004, ADR-005와 같은 이유).
- 「4. 기술 선택」 초안을 확인받으면 기술 스택 ADR(`docs/adr/ADR-<다음 번호>-tech-stack.md`) 초안을 쓰고 목록도 고칩니다(질문 1, 안 1).  
  ADR에는 고른 것과 이유만 쓰고, 원본은 `architecture.md` 「4. 기술 선택」이라고 적습니다.  
  상태는 「검토 중」으로 둡니다. 아키텍처 확정을 기다리지 않고 쓰는 것은 마감 때문에 앱 코드를 일찍 준비할 수 있게 하기 위해서입니다.
- 양식은 `.claude/skills/sdd-architect/template.md` 하나입니다.

**4. 대화 순서**

- 위 「요약」의 흐름을 따릅니다(질문 4, 안 A).
- `requirements.md`가 없으면 시작하지 않고, 요건정리(`/sdd-analyst`)를 안내합니다.
- 시작하면 요건 파일마다 상태를 표로 보여 주고, 확정되지 않은 파일이 있으면 "초안은 쓰고, 확정은 요건이 모두 확정된 뒤에 합니다"라고 알립니다.
- 요건 파일에 커밋하지 않은 수정이 있으면 그렇다고 알리고, 커밋한 것을 기준으로 읽을지 묻습니다. 「읽은 것」의 커밋과 읽은 내용이 같아야 나중에 비교할 수 있기 때문입니다.
- `architecture.md`가 이미 있으면, 먼저 아래 「요건이 바뀌었을 때」를 확인한 뒤 상태를 보고 나눕니다.
  - 작성 중: 이어서 할지 묻고, 질문 대기부터 합니다.
  - 확인 대기: 승인할지, 고칠 곳이 있는지 묻습니다. 팀 검토 사본이 있으면 검토가 끝났는지 묻습니다.
  - 확정: 무엇을 고칠지 묻고, 고치면 확인 대기로 되돌립니다. 스펙이 되돌려 보낸 경우도 여기로 옵니다.
- 새로 시작하면 하는 일과 하지 않는 일을 두세 줄로 알립니다.
- 뼈대: 장 목록, 함께 쓰는 정보의 이름 목록, 갈림길 목록, 넘겨받은 것을 어디서 다룰지를 보여 주고 확인받습니다.  
  확인받으면 `architecture.md`를 만듭니다(작성 중).
- 묻기 전에 찾아보기: 갈림길을 묻거나, 초안을 쓰다가 애매한 곳이 나오거나, 질문 대기에 올리기 전에 앞 단계 자료(요건, `scope.md` 전체, 인터뷰 검토 사본, 참고 자료)에서 관련 대목을 찾습니다.  
  찾은 것은 자료, 대목, 내용, 이 질문과의 관계를 표로 질문 앞에 보여 줍니다. 자료끼리 다르면 함께 보여 주고, 찾은 것이 없으면 찾아본 곳을 말합니다.  
  읽지 못한 자료는 무엇을 못 읽었는지 말하고 내용을 짐작하지 않습니다.
- 갈림길: 안을 둘 이상 놓고, 장점과 단점, 추천과 근거를 붙여 묻습니다.  
  추천의 근거는 요건, 범위, 참고 자료, 공식 문서 가운데서 댑니다. 비용이나 속도 같은 수치는 출처가 있을 때만 씁니다.  
  초안을 쓰다가 새 갈림길이 나오면 그때 묻습니다.
- 초안: 장마다 쓰고 보여 줍니다. 쓰자마자 파일에 남깁니다(ADR-004, ADR-005와 같은 이유). 「탭별로 보기」는 본문 장을 다 쓴 뒤에 씁니다.
- 질문은 질문 도구로 한 번에 4개까지, 추천 답을 첫 선택지로 둡니다.
- 비슷함의 기준값처럼 시험해 봐야 아는 수치는 짐작으로 정하지 않습니다.  
  재는 방법만 정하고, 기준값은 질문 대기에 두거나 "시험 상담으로 정함"이라고 적고 어떻게 정할지(예: 성과측정 탭의 맞는 답으로 비교)를 씁니다.
- 답하다가 요건에서 정한 답과 어긋나면, 요건 파일을 고치지 않고 무엇이 왜 걸리는지 말한 뒤 요건정리로 되돌려 보냅니다.  
  걸린 곳은 질문 대기에 "요건정리로 되돌림"으로 남깁니다.

요건이 바뀌었을 때(에이전트 사이의 약속)

- 부를 때 「읽은 것」의 커밋과, 요건 파일마다 지금의 마지막 커밋(`git log -1 --format=%h -- <파일>`)을 비교합니다.  
  다른 파일이 있거나 새 탭 파일이 생겼으면, 다른 일보다 먼저 이것부터 합니다.
- 다른 파일은 읽은 때의 커밋과 비교(git diff)해 바뀐 요건 번호를 찾습니다. 새 탭 파일은 요건 전체를 새로 들어온 것으로 봅니다.  
  커밋을 찾을 수 없으면 사람에게 바뀐 곳을 묻습니다.
- 바뀐 요건 번호로 「탭별로 보기」와 본문의 근거 칸을 찾아, 바뀐 것, 걸리는 곳, 고칠 안을 표로 보여 주고 확인받은 대로 고칩니다.  
  걸리는 곳이 없으면 그렇다고 말하고, 「읽은 것」만 새것으로 바꿉니다.
- 확정이었으면 확인 대기로 되돌립니다. 확인 대기였으면 확인 대기 그대로 두고, 고친 곳을 다시 확인받습니다.  
  기술 선택이 바뀌면 기술 스택 ADR도 함께 고칩니다.
- 「정한 것」에 "요건 변경으로 고침"과 바뀐 요건 번호, 날짜를 남기고, 「읽은 것」의 상태와 커밋을 새것으로 바꿉니다.

**5. 사람 확인**

| 누가 | 상태 | 확인 칸 |
|---|---|---|
| 쓴 사람이 다 썼다고 말함 | 작성 중 → 확인 대기 | 쓴 사람 (이름, 날짜) |
| 사람이 승인함 (③ 아키텍처 승인) | 확인 대기 → 확정 | 승인 (승인한 사람, 날짜) |

- 확인 대기는 요건이 확정되기 전에도 될 수 있습니다. 요건 검토와 나란히 아키텍처 검토를 하기 위해서입니다.
- 확정은 두 가지가 모두 맞을 때만 합니다.
  - 「읽은 것」의 요건 파일이 모두 확정이고, 읽은 때의 커밋이 지금과 같습니다.
  - 사람이 승인했다고 말했습니다. 누가 승인했는지 말하지 않았으면 묻습니다.
- 요건이 모두 확정되기 전에 승인하겠다고 하면, 확정하지 않고 남은 요건 파일 목록을 알립니다. 상태는 확인 대기로 둡니다.
- 질문 대기가 남아 있으면 확인 대기로 바꾸기 전에 묻습니다. 지금 정할 수 없으면 미룰지 묻고, 「정한 것」에 "미룸"과 이유를 적습니다.
- 확인 대기로 바꿀 때 팀 검토용 사본을 올릴지 묻습니다(ADR-005 질문 4와 같은 방식).  
  올리면 맨 위에 사본 위치를 적고, 검토하는 동안에는 파일을 고치지 않습니다. 검토가 끝나면 의견을 파일로 옮기고 바뀐 곳을 보여 줍니다.  
  검토하는 동안 요건이 바뀌면 고칠 곳만 표로 모아 두고, 검토가 끝난 뒤 의견과 함께 고칩니다.
- 확정할 때 기술 스택 ADR을 채택할지 묻습니다. 채택은 사람이 정합니다.

**6. 지킬 것**

- 요건에서 정한 답을 다시 정하지 않습니다. 고쳐야 하면 요건정리로 되돌려 보냅니다.
- 근거가 없는 수치는 짐작으로 채우지 않습니다(저장소 규칙).
- 사람이 읽는 문서이므로 업무 말로 씁니다.  
  기술 이름(예: 임베딩, LangGraph)은 처음 나올 때 무엇을 하는 것인지 한 줄로 풉니다.  
  장마다 맨 앞에 그 장이 정한 것을 두세 줄로 적어, 기술을 모르는 사람도 무엇을 승인하는지 알게 합니다.
- 실제 고객 정보, 실제 장애 사례, 사내 시스템 이름은 넣지 않습니다(저장소 규칙).  
  연결할 사내 시스템이 필요하면 "상담 시스템", "메신저"처럼 일반 이름으로 씁니다.
- API 키와 비밀번호는 문서에 넣지 않습니다. 「6. 비밀과 시험 자료」에는 키를 어디에 두는지(`.env`, git에 올리지 않음)만 적습니다.

  스펙은 디자인 승인(④)도 끝나야 확정할 수 있으므로, 디자인 상태도 함께 알립니다. 아직 만들지 않은 에이전트면 그렇다고 알립니다.
- 스펙은 아키텍처가 확정되기 전에도 초안을 쓸 수 있습니다(바뀐 약속). 스펙의 확정은 아키텍처와 디자인이 확정된 뒤입니다.

| 9 | 요건이 아직 작성 중인데 승인하겠다고 말합니다. | 확정하지 않고 남은 요건 파일 목록을 알립니다. 상태는 확인 대기입니다. |
| 10 | 요건이 모두 확정되고 바뀐 곳이 없을 때 승인했다고 말합니다. | 확정되고 승인 칸이 채워집니다.<br>기술 스택 ADR을 채택할지 묻고, 다음 단계(스펙)와 디자인 상태를 알려 줍니다. |
| 11 | 갈림길(예: 제품 AI 구성)을 묻는 차례가 됩니다. 범위 질문지에 그 갈림길과 이어지는 팀 의견이 있습니다. | 질문 앞에 요건, `scope.md`, 인터뷰 검토 사본, 참고 자료에서 찾은 대목이 표(자료, 대목, 내용, 관계)로 있습니다. 팀 의견도 그 안에 있습니다.<br>요건이나 `scope.md`에서 정한 답은 다시 묻지 않습니다.<br>「읽은 것」의 참고한 자료에 자료 이름과 읽은 날이 남습니다. |

## 주의할 점

- 이 ADR은 ADR-002가 정하지 않은 "기술 스택 ADR을 누가 쓰나"에 답합니다.  
  HANDOFF의 "기술 스택을 정한다"는 따로 하지 않고 아키텍처 단계에서 합니다.
- 바뀐 약속은 ADR-002(채택)의 「사람이 확인하는 곳」("아키텍처를 승인해야 스펙을 씁니다" 등)과 `docs/guide/sdd.md`의 "확인을 마쳐야 다음 단계로 진행합니다"와 어긋납니다.  
  이 ADR을 채택할 때 ADR-002에 이 ADR을 가리키는 한 줄("초안은 앞 단계 확정 전에도 쓸 수 있고, 확정은 앞 단계 확정 뒤")을 더하고, `sdd.md`도 맞춥니다.
- `requirements.md`와 탭 파일 머리말의 "아키텍처와 디자인은 상태가 확정인 파일만 읽고"도 바뀐 약속과 다릅니다.  
  팀이 노션에서 검토하는 동안에는 원본을 고치지 않으므로, 검토 의견을 옮길 때 요건정리 양식에 맞춰 함께 고칩니다.
- 커밋으로 바뀐 것을 찾으므로, 오타 하나를 고친 커밋에도 다시 보기가 시작됩니다. 걸리는 곳이 없으면 그렇다고 말하고 「읽은 것」만 바꿉니다.
- 아키텍처와 디자인은 서로 읽지 않습니다. 시안에 넣은 정보를 아키텍처가 함께 쓰는 정보에 두지 않았을 수 있습니다.  
  스펙을 쓰다가 찾으면, 어긋난 쪽으로 되돌려 보냅니다(ADR-002).
- 제품 안의 AI 에이전트 구성은 이 에이전트가 정하는 것 가운데 하나입니다. 개발 에이전트(이 ADR의 `sdd-architect`)와 헷갈리지 않게, 문서에서는 "제품 AI"라고 부릅니다.
- 함께 쓰는 정보를 항목 이름까지만 쓰고 칸 형식은 구현 계획으로 넘겼습니다.  
  구현 계획을 탭마다 쓰면 같은 정보의 칸 형식이 탭마다 달라질 수 있습니다. 구현 계획 에이전트를 만들 때 첫 탭에서 정한 형식을 뒤 탭이 따르게 할지 정합니다.
