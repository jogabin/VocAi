# ADR-002 개발 흐름과 개발 에이전트

- 상태: 채택
- 날짜: 2026-10-23 (처음 결정: 2026-10-20)

## 요약

개발은 아래 순서로 진행하려 합니다.  
①~⑦은 AI 작업 후 사람이 확인하는 곳이고, 확인을 마쳐야 다음 단계로 진행하는 구조입니다.

```
인터뷰 ── ① 범위 확인
  ↓
요건정리 ── ② 요건 확정
  ↓
  ├→ 아키텍처 ── ③ 아키텍처 승인
  └→ 디자인 ── ④ 디자인 승인
  ↓ (③과 ④가 모두 끝나면)
스펙 ── ⑤ 스펙 승인
  ↓
구현 계획 ── ⑥ 계획 승인
  ↓
구현
  ↓
검증 ── ⑦ 화면 확인
  ↓
배포·기록
```

개발 에이전트는 대화형 6개와 실행형 4개, 모두 10개입니다.

| 에이전트 | 종류 | 하는 일 | 남기는 것 |
|---|---|---|---|
| 인터뷰 | 대화형 | 범위와 큰 갈림길을 정합니다. | `scope.md` |
| 요건정리 | 대화형 | 화면 탭별로 요건을 자세히 씁니다. | `requirements.md` |
| 아키텍처 | 대화형 | 여러 탭이 같이 쓰는 것을 한곳에서 정합니다. | `architecture.md` |
| 디자인 | 대화형 | 화면 규칙을 정하고 탭마다 시안을 만듭니다. | `style-guide.md`, `mockups/` |
| 스펙 | 대화형 | 탭이 어떻게 동작해야 하는지 정합니다. | `spec.md` |
| 구현 계획 | 대화형 | 지금 코드를 읽고 어떻게 만들지 변경 전과 후를 보여 줍니다. | `plan.md` |
| 백엔드 구현 | 실행형 | `plan.md`대로 서버 쪽 코드를 만듭니다. | 코드 |
| 프론트 구현 | 실행형 | `plan.md`대로 화면 코드를 만듭니다. | 코드 |
| 코드 리뷰 | 실행형 | 코드 품질을 봅니다. | `review.md` |
| QA | 실행형 | 실제로 동작하는지 봅니다. | `qa.md` |

- 대화형은 사람과 대화하며 문서를 만들고, 끝날 때 사람이 확정하거나 승인합니다.
- 실행형은 맡기면 혼자 끝까지 하고 결과를 보고합니다.
- 배포·기록은 에이전트를 따로 두지 않고 axhub 배포 기능을 씁니다.
- 에이전트의 영어 이름은 ADR-003에서 정합니다.

자세한 내용은 아래 「결정」에 있습니다.

## 배경

AI 코딩 도구는 개발 속도를 크게 높여 주지만(1차 팀 회의, 10/14), 만든 코드가 제대로 동작하는지까지 보장하지는 않습니다.  
2차 팀 회의(10/15)에서 짚은 문제도 이것입니다.  
AI가 만든 코드는 빌드를 통과해도, 실제로는 동작하지 않는 기능을 동작하는 것처럼 보이게 만드는 경우가 많습니다.

결과물만 받아 쓰면 문제가 하나 더 생깁니다.  
코드가 어떻게 짜였는지, 시스템이 어떤 순서로 돌고 어떤 구조로 나뉘어 있는지 아무도 모르게 됩니다.  
그런 시스템은 쓰기 편하게 다듬기도, 기능을 덧붙여 넓히기도 어렵습니다.  
사용성과 확장성을 고려한 설계는 요건이 명확하게 정의되어 있고 설계가 먼저 서 있을 때 가능합니다.

그래서 우리는 AI에게 기도하지 않기로 했습니다.  
프롬프트를 던져 놓고 원하는 결과가 나오기를 바라는 대신, 요건과 설계는 사람이 정하고 AI는 그 설계대로 구현하고 검증하는 일을 돕는 도구로 씁니다.  
AI가 사실과 다른 내용을 그럴듯하게 지어내는 할루시네이션도 이 흐름 안에서 걸러 냅니다.  
팀 슬로건도 여기서 나왔습니다.

> Stop praying, start planning. (기도 금지, 설계 시작)

우리가 되려는 것은 AI에게 결과를 비는 개발자가 아니라, AI 에이전트에게 일을 설계해 맡기고 결과를 검증하는 엔지니어(AI Agentic Engineer)입니다.

이 원칙을 개발 흐름으로 옮겼습니다.  
구현을 AI에게 맡기기 전에 요건과 설계는 사람이 확정하고, AI가 만든 결과는 만든 쪽이 아닌 다른 쪽이 검증합니다.

이 흐름은 2026-10-20에 노션 `00. plan`의 Step 1에서 처음 정했습니다.  
그때는 5단계와 에이전트 6개(안 3)를 골랐습니다.  
2026-10-21에 이 결정을 ADR로 옮기면서 다시 검토했고, 안 4로 바꿨습니다.  
이 문서는 Step 1의 결정 9개 가운데 1·2·4·8번(단계, 사람이 확인하는 곳, 에이전트, 검증 순서)을 다룹니다.

2026-10-22에 요건정리 뒤에 디자인 단계를 더했습니다.  
화면을 구현하기 전에 사람이 보기 위해서입니다.  
「검토한 안」은 10/21에 비교한 그대로 두고, 바뀐 내용은 「결정」에 적었습니다.

2026-10-23에 인터뷰 뒤에 사람이 확인하는 곳(① 범위 확인)을 더했습니다.  
요건정리는 확정된 범위만 읽고 시작하므로, 범위도 사람이 확인해야 다음 단계로 넘어갑니다(ADR-004).  
그래서 사람이 확인하는 곳은 7곳이 되고, 원래 ①~⑥은 ②~⑦로 한 칸씩 밀렸습니다.

## 지켜야 할 조건

1. 사람이 확인해야 하는 곳에서는 AI가 혼자 다음 단계로 넘어가지 않습니다.
2. 실제 구현하는 부분과 확인하는 부분을 구분짓습니다.
3. 단계마다 하는 일이 작아서 단계끼리 덜 묶입니다.
4. 앞 단계가 끝난 부분부터 다음 단계를 진행할 수 있습니다.
5. 사람이 한 번에 확인할 양이 적습니다.
6. 구현하기 전에 "어떻게 만들지"까지 사람이 봅니다.

## 검토한 안

### 안 1. 4단계로 짧게 가기

예전에 쓰던 요건 도구의 방식입니다.

```
요구 정리 ─(AI 검토)→ 설계 ─(AI 검토)→ 구현 → 마무리
```

| 구분 | 내용 |
|---|---|
| 장점 | 단계가 적어서 가볍습니다.<br>단계 사이마다 AI 검토가 있습니다.<br>구현하기 전에 계획 문서에서 변경 전과 후를 보여 주고 승인받습니다. |
| 단점 | 이미 있는 화면 하나를 고치는 요청을 한 건씩 처리하는 방식입니다.<br>새 앱 전체를 처음부터 만들기에는 설계 단계가 작고, 계획 문서 하나에 업무 설계와 구현 설계가 함께 들어갑니다.<br>구현한 쪽이 결과를 직접 확인합니다. |
| 결과 | 변경 전과 후를 보고 승인하므로 조건 6은 지킵니다.<br>구현한 쪽이 스스로 확인해서 조건 2는 일부만 지킵니다.<br>요청을 한 건씩 차례로 처리해서 조건 4는 지키지 못합니다. |

### 안 2. 단계를 잘게 나누고 에이전트를 많이 두기

스펙 주도 개발(SDD) 도구의 방식입니다.

```
분류 → 인터뷰 → 요구 문서 → 스펙 → 계획 → 작업 → 실행
에이전트 8개: 백엔드 개발, 프론트 개발, 코드 리뷰, QA, 통합 QA, 요구 문서 검수, 의도 점검 2개
```

| 구분 | 내용 |
|---|---|
| 장점 | 단계가 촘촘하고 검토 에이전트가 많아서 빠뜨리는 것이 적습니다.<br>요구 문서, 스펙, 계획을 나눠서 단계마다 볼 양이 작습니다. |
| 단점 | 마일스톤을 여러 번 돌며 제품을 키우는 팀에 맞춘 방식입니다.<br>계획 단계는 기능마다 기술을 따로 고르는 큰 제품에 맞춘 것입니다. 앱이 하나뿐이면 언어와 프레임워크는 한 번만 정하면 되므로, 기능마다 계획을 세우면 같은 일을 되풀이합니다.<br>분류, 의도 점검, 통합 QA처럼 이 프로젝트에는 필요 없는 단계와 에이전트가 있습니다.<br>계획과 작업 문서는 개발이 끝나면 지웁니다. 우리는 단계마다 만든 문서를 지우지 않고 남기기로 했습니다(README).<br>인터뷰가 기능 단위로 범위를 자릅니다. 우리 요건정의서는 화면 탭별로 씁니다. |
| 결과 | 여섯 조건을 모두 지킵니다.<br>다만 이 프로젝트에 필요 없는 단계와 에이전트까지 만들어야 합니다. |

### 안 3. 5단계, 에이전트 6개

10/20에 처음 고른 안입니다.


| 구분 | 내용 |
|---|---|
| 장점 | 단계가 적어서 만들 에이전트도 적습니다.<br>대화형 단계는 끝날 때 사람이 확정하고, 실행형 단계는 혼자 끝까지 한 뒤 사람이 화면에서 확인합니다. 사람이 끼는 자리가 분명합니다.<br>구현한 에이전트와 확인하는 에이전트가 다르고, 코드 리뷰와 QA도 서로 다른 것을 봅니다. |
| 단점 | 설계서 하나에 아키텍처, 데이터, 요청과 응답, 화면 동작이 모두 들어갑니다.<br>설계 전체가 승인돼야 구현을 시작할 수 있습니다.<br>설계 승인 한 번에 볼 것이 많아서 놓치기 쉽습니다.<br>구현 계획 문서가 없어서 어떻게 만들지는 구현 에이전트가 혼자 정합니다. |

## 결정

안 4로 정했습니다.  
여섯 조건을 모두 지키는 안은 안 2와 안 4입니다.  
그중 이 프로젝트에 필요 없는 단계와 에이전트를 두지 않는 안 4를 골랐습니다.

그 뒤 2026-10-22에 안 4의 요건정리 뒤에 디자인 단계를 더했습니다.

```
인터뷰 → 요건정리 → 아키텍처·디자인(나란히) → 스펙 → 구현 계획 → 구현 → 검증 → 배포·기록
```

**단계와 에이전트**

| 단계 | 에이전트 | 종류 | 두는 곳 |
|---|---|---|---|
| 인터뷰 | 인터뷰 | 대화형 | `.claude/skills/` |
| 요건 | 요건정리 | 대화형 | `.claude/skills/` |
| 아키텍처 | 아키텍처 | 대화형 | `.claude/skills/` |
| 디자인 | 디자인 | 대화형 | `.claude/skills/` |
| 스펙 | 스펙 | 대화형 | `.claude/skills/` |
| 구현 계획 | 구현 계획 | 대화형 | `.claude/skills/` |
| 구현 | 백엔드 구현, 프론트 구현 | 실행형 | `.claude/agents/` |
| 검증 | 코드 리뷰, QA | 실행형 | `.claude/agents/` |
| 배포·기록 | 없음 (axhub 배포 기능을 씀) | | |

대화형 6개와 실행형 4개, 모두 10개입니다.

```
.claude/
├── skills/        대화형 에이전트 6개
│   ├── 인터뷰
│   ├── 요건정리
│   ├── 아키텍처
│   ├── 디자인
│   ├── 스펙
│   └── 구현 계획
└── agents/        실행형 에이전트 4개
    ├── 백엔드 구현
    ├── 프론트 구현
    ├── 코드 리뷰
    └── QA
```

에이전트의 영어 이름과 자리는 ADR-003에서 정합니다.

- 대화형 에이전트는 사람과 대화하며 문서를 만듭니다.
- 실행형 에이전트는 맡기면 혼자 끝까지 하고 결과를 보고합니다.

대화형 단계에는 결과를 검사하는 에이전트를 따로 두지 않습니다.  
사람과 대화하며 만들고, 끝날 때 사람이 확정하거나 승인하기 때문입니다.

각 단계를 전체에 한 번 할지 탭마다 할지는 에이전트에 정해 두지 않습니다.  
전체를 한 번에 하거나, 한 번에 해 두고 탭마다 보거나, 처음부터 탭마다 하는 것 중에서 그때그때 대화로 정합니다.

**단계를 이렇게 나눈 이유**

- 인터뷰를 요건정리 앞에 둡니다.  
  지금 가진 자료끼리 서로 다르기 때문입니다.  
  v2 요건정의서는 관리자 승인 단계를 범위에서 뺐는데, 3차 회의에서는 넣을지 더 보기로 했습니다.  
  심각도 기준도 1차 회의와 v2가 다릅니다.  
  이런 갈림길과 범위를 먼저 정하면 뒤 단계가 다룰 양이 줄고, 요건정리는 화면 탭별로 자세히 쓰는 일에 집중할 수 있습니다.
- 아키텍처를 스펙보다 먼저 둡니다.  
  여러 탭이 같이 쓰는 것(예: 장애 정보)을 한곳에서 먼저 정해야 탭 스펙끼리 어긋나지 않습니다.
- 디자인을 요건정리 뒤에, 아키텍처와 나란히 둡니다(2026-10-22에 더함).  
  디자인 단계가 없으면 사람이 화면을 처음 보는 때가 구현이 끝난 뒤의 화면 확인입니다.  
  그때 화면 모양이 생각과 다르면 구현까지 되돌아가야 합니다.  
  색, 글꼴, 간격 같은 화면 규칙은 여러 탭이 같이 쓰는 것이라 먼저 한 번 정하고, 탭마다 시안을 만들어 구현 전에 사람이 봅니다.  
  아키텍처와 디자인은 둘 다 요건정의서를 읽고 쓰므로 나란히 진행할 수 있습니다. 스펙은 둘 다 승인된 뒤에 씁니다.
- 구현 계획을 스펙과 구현 사이에 둡니다.  
  스펙만 있으면 어떻게 만들지를 구현 에이전트가 혼자 정합니다.  
  그러면 스펙은 맞춰도 원하는 모양과 다르게 나올 수 있습니다.  
  그래서 지금 코드를 읽고 변경 전과 후를 보여 주는 계획을 사람이 승인한 뒤에 구현합니다.

**남기는 것**

| 단계 | 남기는 것 | 파일 | 폴더 |
|---|---|---|---|
| 인터뷰 | 범위 | `scope.md` | `docs/requirements/` |
| 요건 | 요건정의서 | `requirements.md` | `docs/requirements/` |
| 아키텍처 | 아키텍처 | `architecture.md` | `docs/architecture/` |
| 디자인 | 화면 규칙 | `style-guide.md` | `docs/design/` |
| 디자인 | 화면 시안 | 탭마다 (형식은 디자인 에이전트를 만들 때 정함) | `docs/design/mockups/` |
| 스펙 | 스펙 | `spec.md` | `docs/spec/` |
| 구현 계획 | 구현 계획 | `plan.md` | `docs/plan/` |

`docs/spec/`과 `docs/plan/`은 ADR-001에서 만든 설계 폴더와 작업 폴더(`docs/tasks/`)의 이름을 바꾼 것입니다.  
설계 단계가 아키텍처와 스펙으로 나뉘면서 설계 폴더에는 스펙만 남았기 때문입니다.  
폴더 이름을 안에 든 파일과 맞춰서, 이름만 보고도 무엇이 들었는지 알 수 있게 했습니다.  
ADR-001의 설계 폴더는 이름이 `design/`이었지만, 지금 이 저장소에서 design은 화면 디자인만 뜻합니다(2026-10-22).

**사람이 확인하는 곳**

1. 범위 확인: 인터뷰를 한 사람이나 팀원이 `scope.md`를 확인해야 요건정리를 시작합니다(2026-10-23에 더함).
2. 요건 확정: 요건을 정리한 사람이 먼저 보고, 팀 회의에서 팀원이 확인합니다.
3. 아키텍처 승인: 아키텍처를 승인해야 스펙을 씁니다.
4. 디자인 승인: 화면 규칙과 그 탭의 시안을 승인해야 스펙을 씁니다.
5. 스펙 승인: 스펙을 승인해야 구현 계획을 씁니다.
6. 계획 승인: `plan.md`를 승인해야 구현을 맡깁니다.
7. 화면 확인: 코드 리뷰와 QA가 끝나면 사람이 배포된 화면을 직접 눌러 봅니다.

**"되는 척"을 막는 순서**

1. 구현 에이전트는 결과를 보고할 때 확인한 것과 확인하지 못한 것을 나눠 적습니다.
2. 코드 리뷰 에이전트는 코드 품질을, QA 에이전트는 실제 동작을 봅니다.
3. 마지막에 사람이 화면에서 확인합니다.

`test.md`는 `plan.md`의 「검증」을 바탕으로 테스트 항목, 방법, 기대 결과를 적습니다.  
결과 칸은 확인하면서 채웁니다.

## 주의할 점

- 여기서 말하는 에이전트는 우리가 개발할 때 쓰는 에이전트입니다.  
  제품 안에서 장애를 찾는 AI 에이전트와는 다릅니다.  
  제품 에이전트는 요건정리를 마친 뒤 정합니다.
- 아키텍처와 디자인은 나란히 진행하므로 서로 어긋날 수 있습니다.  
  예를 들어 시안에 넣은 정보를 아키텍처에서는 저장하지 않기로 했을 수 있습니다.  
  스펙을 쓰다가 어긋난 것을 찾으면, 어긋난 쪽 단계로 돌아가 고치고 다시 승인받습니다.
- 구현 계획 에이전트는 요건정의서, 아키텍처, 화면 규칙(`style-guide.md`)과 그 탭의 시안, 스펙, 지금 코드, 기술 스택 ADR을 읽고 씁니다.  
  첫 탭은 아직 코드가 없어서 `plan.md`가 새로 만들 파일과 그 역할 정도로 얇습니다.
- `test.md`를 구현 에이전트가 만들지 QA 에이전트가 만들지는 구현 에이전트를 만들 때 정합니다.
- 탭별로 나눠 쓸 때 파일 이름을 어떻게 붙일지는 요건정리 에이전트를 만들 때 정합니다.
- 대화형 에이전트 안에서 AI가 한 번 더 검토할지는 스킬마다 만들 때 정합니다.
