# ADR-008 디자인 에이전트

- 상태: 검토 중
- 날짜: 2026-10-24

> 적용 범위: 「질문 2」(화면 부품을 axhub 기본 틀의 HeroUI v3로 한다)와 기본 틀을 설명한 부분은, 디자인 에이전트를 만들던 때(10/24)에 시연용 구현이 그 기본 틀로 만들어진다고 보고 정한 것입니다.  
> 제출 구현(VocAi)은 Vue 3로 화면을 만들어 그 부분은 적용되지 않습니다([ADR-010](ADR-010-submission-implementation.md)).  
> 디자인 에이전트가 일하는 순서(참고 받기 → 화면 규칙 → 탭별 시안)는 그대로입니다.

## 요약

디자인은 요건(`requirements.md`와 탭 파일)을 읽고, 화면이 어떻게 보이는지 정하는 단계입니다.  
여러 탭이 같이 쓰는 화면 규칙(색, 글자, 간격, 부품 모양)을 `docs/design/style-guide.md`에 먼저 정하고, 탭마다 시안을 `docs/design/mockups/`에 만듭니다.

시작하면 참고할 디자인부터 받습니다(팀 요청, 2026-10-24).  
웹 주소, 화면 캡처, 이미지 파일, 말로 된 바람 가운데 무엇이든 받습니다. 에이전트가 직접 열어 보고, 「가져올 것」과 「가져오지 않을 것」을 나눠 확인받습니다.  
가져올 것은 색, 글자, 간격 같은 일반 값으로 바꿔 화면 규칙에 적습니다. 로고, 이름, 그림, 문구, 내부 화면은 저장소에 넣지 않습니다(「질문 1」).

화면 규칙은 axhub 기본 틀(my-first-app)의 화면 부품과 디자인 규칙 검사를 그대로 쓰고, 색 같은 값만 참고 디자인에 맞춰 바꿔 얹습니다(「질문 2」).  
시안은 탭마다 브라우저로 열어 보는 HTML 한 장과, 무엇을 왜 거기 두었는지 적은 설명 한 장입니다(「질문 3」).  
화면 규칙과 시안은 상태를 따로 둡니다. 탭의 스펙은 화면 규칙과 그 탭의 시안이 확정되면 확정할 수 있습니다(「질문 4」).

```
요건 파일을 읽는다 (작성 중이어도 읽음, 파일마다 상태와 커밋을 남김)
  ↓
참고 디자인을 받는다 (웹 주소, 화면 캡처, 이미지·PDF, 말로 된 바람, 없음)
  ↓

  ↓

  ↓
화면 규칙을 장마다 쓴다 → 색과 글자는 견본 화면과 함께 보여 준다
  ↓
탭마다 시안: 화면 구성(글)을 확인받는다 → HTML 시안과 찍은 화면을 보여 준다 → 고칠 곳을 받는다
  ↓            ↖ 요건 파일이 바뀌면: 커밋을 비교해 바뀐 요건 번호를 찾고, 걸리는 시안만 고친다

  ↓

```

디자인과 앞뒤 단계의 경계는 이렇게 정했습니다.

| 디자인이 쓰는 것 | 쓰지 않는 것 (정한 단계 또는 넘길 단계) |
|---|---|
| 화면 규칙: 색, 글자, 간격, 모서리, 부품 모양, 아이콘 | 무엇을 보여 줘야 하나, 업무 규칙과 수치 (요건정리) |
| 탭마다 배치: 무엇이 어디에 어떤 모양으로 보이나 | 버튼을 누르면 무엇이 일어나나, 화면 이동, 서버에 무엇을 요청하나 (스펙) |
| 상태별 모양: 불러오는 중, 빈 화면, 오류, AI 진행 단계 | 함께 쓰는 정보의 항목과 상태 값 (아키텍처) |
| 넘겨받은 것: 화면 모양, 모니터 표시 방식, 팀 아이콘, AI 진행 단계 모양(1-06), 기본 틀을 따를지 | 부품 묶음 설치, 파일, 코드 (구현 계획, 구현) |

"보이나, 안 보이나"는 요건이고, "어디에 어떤 모양으로 보이나"는 디자인이며, "누르면 어떻게 되나"는 스펙입니다.

- 묻기 전에 요건, 범위, 인터뷰 검토 사본, 참고 자료에서 관련 대목을 찾아 질문에 붙입니다(ADR-006과 같음).
- 시험 장면은 12개이고, 「결정」 8번에 있습니다.

## 배경

ADR-002에서 정한 개발 에이전트 10개 가운데 네 번째인 디자인 에이전트(`sdd-designer`)를 만듭니다.  
ADR-003의 만드는 순서에서 첫 단계(에이전트 ADR 쓰기)에 해당합니다.

ADR-002는 2026-10-22에 디자인 단계를 요건정리 뒤, 아키텍처와 나란히 두었습니다.  
디자인 단계가 없으면 사람이 화면을 처음 보는 때가 구현이 끝난 뒤이기 때문입니다.  
스펙은 아키텍처와 디자인이 둘 다 승인된 뒤에 확정합니다(ADR-006에서 바뀐 약속).

앞 단계에서 디자인으로 넘겨 둔 것이 있습니다.

- 범위(`scope.md`)의 「다른 단계로 넘길 것」: 화면 모양, 모니터 표시 방식, 팀 아이콘(협의요청 10/22)
- 요건(`requirements.md`)의 「다른 단계로 넘길 것」: AI 진행 단계를 보여 주는 모양(로딩 표시 등, 1-06)
- 아키텍처(`architecture.md`)의 「다른 단계로 넘길 것」: axhub 기본 틀(my-first-app)을 앱 뼈대로 쓸지, 그 안의 화면 부품 묶음과 배포 전 디자인 규칙 검사를 따를지 (구현 계획과 함께)
- ADR-002 「남기는 것」: 시안의 형식은 디자인 에이전트를 만들 때 정함

이 단계에서 함께 정할 것이 세 가지 있습니다.

- 원하는 화면 느낌을 어떻게 받나.  
  팀은 공개된 은행 홈페이지와 비슷한 느낌을 원하고, 참고할 디자인(웹 주소 등)을 받는 절차가 있으면 좋겠다고 했습니다(2026-10-24).
- 참고로 받는 화면이 그룹웨어 같은 내부 화면일 수도 있습니다.  
  저장소 규칙상 사내 시스템 이름과 내부 화면은 저장소에 넣지 않으므로, 일반 규칙으로 바꿔 쓰는 방법이 필요합니다(HANDOFF 2026-10-24).
- 마감은 사전 제출 10/30(금) 24:00입니다(노션 「04. 본선 진출 안내」, 10/24 공지).  
  탭이 7개라 시안을 가볍게 만들어야 합니다.

## 정할 것

ADR-003의 「에이전트 ADR에 쓸 것」 8가지를 정합니다.

| 항목 | 무엇을 정하나 | 지금 아는 것 |
|---|---|---|
| 1. 하는 일 | 디자인이 쓰는 것과 쓰지 않는 것 | 화면 규칙을 정하고 탭마다 시안을 만듦 (ADR-002) |
| 2. 읽는 것 | 무엇을 읽고 시작하나 | 요건, 작성 중이어도 읽음 (바뀐 약속, ADR-006)<br>참고 디자인을 어떻게 받나는 **질문 1** |
| 3. 남기는 것 | 화면 규칙과 시안의 모양 | `style-guide.md`, `mockups/` (ADR-002)<br>화면 규칙을 무엇 위에 얹나는 **질문 2**, 시안의 형식은 **질문 3** |
| 4. 대화 순서 | 어떻게 묻고 쓰나 | 참고 받기 → 화면 규칙 → 탭마다 시안 |
| 5. 사람 확인 | 누가 무엇을 확정하나 | 화면 규칙과 그 탭의 시안을 승인해야 스펙을 씀 (ADR-002 ④)<br>상태를 어떻게 나누나는 **질문 4** |
| 6. 지킬 것 | 하면 안 되는 것 | 저장소 규칙, 에이전트 사이의 약속 |
| 7. 다음 단계로 넘기기 | 스펙과 구현 계획이 무엇을 이어받나 | 확정된 화면 규칙과 그 탭의 시안 |
| 8. 시험 장면 | 3개 이상, 각각 무엇이 나오면 통과인지 | 아직 정하지 않음 |

## 질문 1. 참고 디자인을 어떻게 받고 쓰나

### 지켜야 할 조건

1. 사람이 원하는 느낌을 말뿐 아니라 실제 자료(웹 주소, 캡처)로 줄 수 있습니다(팀 요청).
2. 저장소에 실제 회사의 로고, 이름, 그림, 문구, 내부 화면이 들어가지 않습니다(저장소 규칙).
3. 화면 규칙의 값마다 어디서 왔는지 남습니다(저장소 규칙: 근거 없는 수치 금지).
4. 에이전트가 참고를 실제로 보고 판단합니다. 보지 못한 것은 짐작하지 않습니다(에이전트 사이의 약속).

### 에이전트가 참고를 볼 수 있나 (2026-10-24 시험)

공개된 은행 홈페이지 하나로 시험했습니다.

| 방법 | 결과 |
|---|---|
| 웹 주소를 이 PC의 Chrome으로 화면 없이 띄워(헤드리스) 찍기 | 첫 화면 전체가 찍혔고, 에이전트가 찍은 화면을 보고 색, 배치, 글자 크기를 읽을 수 있었습니다.<br>첫 화면에 뜬 안내 팝업도 함께 찍혔습니다. |
| 주소의 HTML만 받아 색 값 찾기 | 찾지 못했습니다. 그 사이트는 첫 HTML이 화면 틀(프레임)과 스크립트뿐이라 색 값이 들어 있지 않았습니다. |
| 찍은 화면에서 점을 골라 색 값 뽑기 | 뽑을 수 있었습니다.<br>다만 팝업이 깔아 둔 반투명 가림막 아래의 점은 원래보다 어둡게 나왔습니다. |
| 로그인해야 보이는 화면, 사내 화면 | 시험하지 않았습니다. 에이전트에게 로그인 정보를 주지 않으므로 사람이 캡처해 줘야 합니다. |

그래서 웹 주소는 찍은 화면을 보고 판단하고, 색 값은 가림막이 없는 곳에서 뽑은 뒤 견본 화면으로 사람이 확인하게 합니다.

### 안 1. 시작할 때 참고를 받고, 가져올 것만 일반 값으로 옮기기

1. 무엇을 참고할지 묻습니다. 웹 주소, 화면 캡처나 이미지·PDF(`_raw/design/`에 두고 경로를 알려 줌), 말로 된 바람("차분한 파랑 계열" 등), 없음 가운데 몇 개든 받습니다.
2. 참고마다 무엇이 마음에 드는지(색, 글자, 배치, 분위기, 전체) 묻습니다.
3. 에이전트가 열어 봅니다. 웹 주소는 위 방법으로 찍어 `_raw/design/`에 남기고 봅니다.
4. 「가져올 것 / 가져오지 않을 것」 표를 보여 주고 확인받습니다.
5. 화면 규칙에는 값과 근거("참고 1에서 뽑음, 10/24")만 적습니다. 캡처와 찍은 화면은 `_raw/`(git 밖)에만 둡니다.

표는 이런 모양입니다. 예시는 설명을 위해 지어낸 것입니다.

| 참고 | 가져올 것 | 가져오지 않을 것 |
|---|---|---|
| 참고 1. 공개 은행 홈페이지 (웹 주소) | 밝은 파랑 강조색과 짙은 남색, 흰 바탕에 얇은 회색 테두리 카드, 위쪽 가로 메뉴, 작은 글자와 촘촘한 목록 | 로고, 은행 이름, 캐릭터 그림, 행사 문구, 상품 이름 |
| 참고 2. 내부 업무 화면 캡처 (사람이 줌) | 위에 조회 조건, 아래에 표를 두는 배치. 표 한 줄의 높이 | 화면 이름, 메뉴 이름, 사람 이름, 화면 속 실제 정보 |

| 구분 | 내용 |
|---|---|
| 장점 | 사람이 원하는 느낌을 자료로 주고, 무엇을 가져올지 사람이 고릅니다.<br>저장소에는 일반 값만 남아서 내부 화면을 참고해도 규칙에 어긋나지 않습니다.<br>값마다 근거가 남습니다. |
| 단점 | 처음에 묻고 열어 보는 일이 하나 늘어납니다.<br>찍은 화면에서 뽑은 색은 실제 값과 조금 다를 수 있습니다. 그래서 견본 화면으로 사람이 확인합니다. |

### 안 2. 참고 없이 기본 틀의 디자인을 그대로 쓰기

## 질문 2. 화면 규칙을 무엇 위에 얹나

### 지금 아는 것

axhub 기본 틀(my-first-app, 2026-10-24에 읽음)의 화면 쪽은 이렇습니다.

- 부품은 HeroUI v3(버튼, 입력, 표, 카드, 모달 등), 아이콘은 Phosphor, 배치는 Tailwind 4입니다.  
  모양과 색은 axhub 디자인 시스템 패키지(`@jocoding-ax-partners/design-system`)가 칠하며, axhub 콘솔과 같은 모양입니다(`AGENTS.md` 「디자인」).
- 배포 전에 디자인 규칙 검사(`scripts/check-design.sh`, `axhub.yaml`의 `ci.commands`)가 돕니다.  
  화면 코드에 색 값(`#2d64fa`)이나 크기 값(`15px`)을 직접 쓰거나, Tailwind 기본 색(`text-gray-500`)을 쓰거나, 다른 부품 묶음을 가져오면 배포가 막힙니다.

- 패키지의 색은 이름 붙은 값(CSS 변수)으로 정해져 있습니다. 예: 강조색 `--primary-base: #2d64fa` (패키지 4.2.0 `dist/styles/index.css`).

## 결정

질문 1은 안 1(가져올 것만 일반 값으로 옮기기), 질문 2는 안 가(기본 틀의 부품과 검사를 따르고 값만 바꿔 얹기), 질문 3은 안 B(탭마다 HTML 시안과 설명), 질문 4는 안 ㄱ(화면 규칙 하나, 시안은 탭마다 상태)으로 정했습니다(2026-10-24, 모두 추천대로).

아래는 ADR-003의 「에이전트 ADR에 쓸 것」 8가지 순서입니다.

**1. 하는 일**

- 하는 일: 참고 디자인을 받아 일반 값으로 바꾸고, 여러 탭이 같이 쓰는 화면 규칙을 정하고, 탭마다 시안을 만듭니다.  
  앞 단계가 디자인으로 넘긴 것(화면 모양, 모니터 표시 방식, 팀 아이콘, AI 진행 단계 모양 1-06)을 다룹니다.
- 하지 않는 일: 요건에서 정한 답(무엇을 보여 줘야 하나, 업무 규칙, 수치)을 다시 정하지 않습니다. 시안에 요건에 없는 정보를 넣지 않습니다.  
  화면 동작, 화면 이동, 서버 요청, 부품 묶음 설치, 파일과 코드는 쓰지 않고 넘길 단계와 함께 「다른 단계로 넘길 것」에 적습니다.

경계는 「요약」의 표를 따르고, 애매하면 두 가지로 판단합니다.

- 여러 탭이 같이 쓰는 겉모습이면 화면 규칙, 탭 하나의 배치면 그 탭의 시안입니다.
- 시안을 그리다 요건에 없는 정보가 필요하면, 넣지 않고 요건정리로 되돌려 보냅니다.

"장애 목록"을 예로 들면 이렇습니다. 예시는 설명을 위해 지어낸 것입니다.

| 무엇 | 예 | 어느 단계 |
|---|---|---|
| 업무 규칙 | 목록에서 장애마다 등급과 영향받은 고객 수를 알 수 있어야 한다. | 요건정리 |
| 화면 규칙 | 등급은 색 배지로 보인다. P1은 빨강 계열, P4는 회색 계열이다. 강조색은 밝은 파랑이다. | 디자인 (화면 규칙) |
| 시안 | 위에 조회 조건, 아래에 표. 등급 배지는 맨 앞 칸. 장애가 없으면 표 자리에 "처리할 장애가 없습니다"가 보인다. | 디자인 (시안) |
| 화면 동작 | 줄을 누르면 상세가 열린다. 화면은 몇 초마다 목록을 다시 묻는다. | 스펙 |
| 파일과 코드 | 이 화면은 이 파일에 만들고, `tokens.css`의 값은 `app/globals.css`로 옮긴다. | 구현 계획 |

**2. 읽는 것**

- `docs/requirements/requirements.md`와 `docs/requirements/tabs/`의 탭 파일을 상태와 상관없이 읽습니다(바뀐 약속).  
  `requirements.md`가 없으면 시작하지 않습니다.
- `requirements.md`와 `scope.md`의 「다른 단계로 넘길 것」 가운데 넘길 단계가 디자인인 것을 하나도 빠짐없이 본문, 정한 것, 질문 대기, 다른 단계로 넘길 것 가운데 한 곳으로 옮깁니다.
- 기술 스택 ADR과 앱 기본 틀의 디자인 지침을 읽습니다. 화면 규칙을 얹을 바탕이기 때문입니다(질문 2).  
  기본 틀은 저장소 밖에 있으므로 「읽은 것」에 어디서 읽었는지와 판(커밋이나 패키지 판)을 적습니다.
- 아키텍처 문서는 읽지 않습니다. 둘은 나란히 진행하고, 어긋난 것은 스펙에서 찾아 되돌려 보냅니다(ADR-002).  
  AI 진행 단계의 이름도 요건 1-06에 있어서 아키텍처를 읽지 않아도 됩니다.
- 참고 디자인은 사람에게 받습니다(질문 1).
- 묻거나 애매한 곳이 생기면, 묻기 전에 요건 → `scope.md` 전체 → 인터뷰 검토 사본 → 참고 자료 순서로 관련 대목을 찾아 질문에 붙입니다(ADR-006과 같음).  
  예전 화면 설계(v2 화면설계서 등)는 배치를 볼 때 참고만 하고 그대로 따르지 않습니다.
- 우리 프로젝트에서 무엇을 읽는지는 설명서에 적지 않습니다. 설명서는 다른 일에도 쓸 수 있게 둡니다.

**3. 남기는 것**

- 「요약」의 파일 모양대로 남깁니다(질문 2 안 가, 질문 3 안 B, 질문 4 안 ㄱ).
- `style-guide.md`  
  맨 위: 상태와 확인, 팀 검토 사본 위치  
  읽은 것: 요건 파일마다 읽은 때의 상태와 커밋, 기본 틀을 읽은 곳과 판, 참고 디자인 목록(번호, 종류, 이름이나 일반 이름, 공개 주소, 본 날)  
  본문: 1. 참고 디자인, 2. 한눈에 보기, 3. 색, 4. 글자, 5. 간격과 모서리, 6. 부품, 7. 화면 뼈대, 8. 상태 표시, 9. 탭별로 보기  
  끝: 정한 것, 질문 대기, 다른 단계로 넘길 것
- 색은 표로 씁니다. 칸은 의미 이름, 값(밝은 화면, 어두운 화면을 쓰면 그 값도), 기본 틀의 이름, 쓰는 곳, 근거입니다.  
  근거에는 "참고 1에서 뽑음(본 날)", "기본 틀의 기본값", "사람이 고름(이름, 날짜)" 가운데 하나를 적습니다.  
  등급(P1~P4), 처리 상태, 승인 상태처럼 요건에 정해진 값을 색으로 나눌 때는 요건 번호도 적습니다.
- 글자와 바탕의 밝기 차이(대비)는 웹 접근성 기준 WCAG 2.1의 AA(보통 글자 4.5 대 1, 큰 글자 3 대 1)를 넘는지 확인하고 결과를 적습니다.  
  참고에서 뽑은 색이 기준에 못 미치면 그대로 쓰지 않고 안을 붙여 묻습니다.
- `tokens.css`에는 화면 규칙의 값만 기본 틀의 이름 그대로 모읍니다. 시안이 이 파일을 읽고, 구현은 이 값을 `app/globals.css`로 옮깁니다.  
  `style-guide.md`의 색·글자 표와 이 파일은 같은 값이어야 합니다. 원본은 `style-guide.md`이고, 고치면 둘을 함께 고칩니다.
- 시안 설명(`mockups/<번호>-<탭>.md`)  
  맨 위: 상태와 확인  
  읽은 것: 그 탭 파일과 `requirements.md`의 상태와 커밋, 읽은 `style-guide.md`의 커밋  
  본문: 화면 구성(영역마다 무엇이 있나와 요건 번호), 상태별 모양, 쓴 부품  
  끝: 정한 것, 질문 대기, 다른 단계로 넘길 것
- 시안(`.html`)은 가상 데이터만 씁니다. `tokens.css` 말고 다른 파일이나 외부 주소는 글꼴 정도만 씁니다.
- 찍은 화면(`.png`)은 시안을 고칠 때마다 다시 찍습니다.
- 디자인에서 물어서 정한 것은 「정한 것」에 고른 답, 고르지 않은 안, 이유와 함께 남깁니다(ADR-004~006과 같은 이유).
- 양식은 `.claude/skills/sdd-designer/`의 `template.md`(화면 규칙)와 `template-mockup.md`(시안 설명) 두 개입니다.

**4. 대화 순서**

- 위 「요약」의 흐름을 따릅니다.
- `requirements.md`가 없으면 시작하지 않고, 요건정리(`/sdd-analyst`)를 안내합니다.
- 시작하면 요건 파일마다 상태를 표로 보여 주고, 확정되지 않은 파일이 있으면 "초안은 쓰고, 확정은 요건이 모두 확정된 뒤에 합니다"라고 알립니다.
- 요건 파일에 커밋하지 않은 수정이 있으면 그렇다고 알리고, 커밋한 것을 기준으로 읽을지 묻습니다(ADR-006과 같은 이유).
- `style-guide.md`가 이미 있으면, 먼저 아래 「요건이 바뀌었을 때」를 확인한 뒤 화면 규칙과 시안의 상태를 표로 보여 주고 이어서 할 곳을 묻습니다.
- 새로 시작하면 하는 일과 하지 않는 일을 두세 줄로 알립니다.
- 참고 받기: 무엇을 참고할지 한 번에 묻습니다. 웹 주소, 캡처·이미지·PDF(`_raw/design/`에 두고 경로를 알려 달라고 함), 말로 된 바람, 없음 가운데 몇 개든 받습니다.  
  참고마다 마음에 드는 점(색, 글자, 배치, 분위기, 전체)과 피하고 싶은 점을 묻습니다.  
  "없음"이면 기본 틀의 디자인으로 시작하고, 근거를 "기본 틀의 기본값"으로 적습니다.
- 참고 열어 보기: 웹 주소는 화면 없는 브라우저로 넓은 화면을 찍어 `_raw/design/`에 남기고 봅니다.  
  팝업이 가리면 그렇다고 말하고, 가리지 않은 곳에서 값을 뽑거나 사람에게 캡처를 부탁합니다.  
  로그인이 필요하거나 열리지 않으면 내용을 짐작하지 않고 캡처를 부탁합니다.
- 「가져올 것 / 가져오지 않을 것」 표를 보여 주고 확인받습니다.
- 뼈대: 장 목록, 넘겨받은 것을 어디서 다룰지, 갈림길 목록(예: 어두운 화면을 쓸지), 시안을 만들 탭의 순서를 보여 주고 확인받습니다.  
  확인받으면 `style-guide.md`를 만듭니다(작성 중). 시안 순서는 핵심 흐름 탭(상담등록, 장애목록, 알림승인)부터 권합니다(범위 질문지 6번).
- 화면 규칙: 장마다 쓰고 보여 줍니다. 쓰자마자 파일에 남깁니다.  
  색과 글자는 글만으로 판단하기 어려우므로, 견본(`style-guide.html`)을 찍은 화면과 함께 보여 줍니다.
- 시안: 탭마다 화면 구성(글)을 먼저 확인받고, 그다음 HTML 시안과 찍은 화면을 보여 줍니다.  
  고칠 곳을 받으면 고치고 다시 찍어 보여 줍니다.
- 묻기 전에 찾아보기: 갈림길을 묻거나 질문 대기에 올리기 전에 앞 단계 자료에서 관련 대목을 찾아 표(자료, 대목, 내용, 관계)로 질문 앞에 보여 줍니다(ADR-006과 같음).
- 갈림길: 안을 둘 이상 놓고 장점과 단점, 추천과 근거를 붙여 묻습니다. 색처럼 눈으로 봐야 하는 갈림길은 안마다 견본을 붙입니다.  
  추천의 근거는 참고 디자인, 요건, 기본 틀 지침, 접근성 기준 가운데서 댑니다.
- 질문은 질문 도구로 한 번에 4개까지, 추천 답을 첫 선택지로 둡니다.
- 답하다가 요건에서 정한 답과 어긋나거나 요건에 없는 정보가 필요하면, 요건 파일을 고치지 않고 요건정리로 되돌려 보냅니다.  
  화면 동작 이야기(누르면 어떻게 되나)가 나오면 「다른 단계로 넘길 것」에 스펙으로 적습니다.

요건이 바뀌었을 때(에이전트 사이의 약속)

- 부를 때 「읽은 것」의 커밋과 요건 파일마다 지금의 마지막 커밋을 비교합니다. 다른 파일이 있으면 다른 일보다 먼저 이것부터 합니다.
- 다른 파일은 읽은 때의 커밋과 비교(git diff)해 바뀐 요건 번호를 찾고, 시안 설명의 요건 번호로 걸리는 시안을 찾습니다.  
  바뀐 것, 걸리는 시안과 화면 규칙, 고칠 안을 표로 보여 주고 확인받은 대로 고칩니다. 걸리는 곳이 없으면 「읽은 것」만 바꿉니다.
- 확정이었던 파일을 고치면 확인 대기로 되돌립니다. 「정한 것」에 "요건 변경으로 고침"과 바뀐 요건 번호, 날짜를 남깁니다.

화면 규칙을 고쳤을 때

- 값만 바뀌면 시안은 `tokens.css`를 읽으므로 따라 바뀝니다. 찍은 화면을 다시 찍고, 시안의 상태는 그대로 둡니다.
- 배치나 부품이 바뀌어 시안을 고쳐야 하면, 걸리는 시안을 표로 보여 주고 고친 시안은 확인 대기로 되돌립니다.

**5. 사람 확인**

| 누가 | 상태 | 확인 칸 |
|---|---|---|
| 쓴 사람이 다 썼다고 말함 | 작성 중 → 확인 대기 | 쓴 사람 (이름, 날짜) |
| 사람이 승인함 (④ 디자인 승인) | 확인 대기 → 확정 | 승인 (승인한 사람, 날짜) |

- 상태는 `style-guide.md`에 하나, 시안 설명마다 하나 있습니다(질문 4, 안 ㄱ).
- 화면 규칙은 두 가지가 모두 맞을 때만 확정합니다.
  - 「읽은 것」의 요건 파일이 모두 확정이고, 읽은 때의 커밋이 지금과 같습니다.
  - 사람이 승인했다고 말했습니다. 누가 승인했는지 말하지 않았으면 묻습니다.
- 시안은 위 두 가지에 더해 화면 규칙이 확정이어야 확정합니다.
- 요건이 모두 확정되기 전에 승인하겠다고 하면, 확정하지 않고 남은 요건 파일 목록을 알립니다. 상태는 확인 대기로 둡니다.
- 질문 대기가 남아 있으면 확인 대기로 바꾸기 전에 묻습니다. 지금 정할 수 없으면 미룰지 묻고, 「정한 것」에 "미룸"과 이유를 적습니다.
- 확인 대기로 바꿀 때 팀 검토용 사본을 올릴지 묻습니다(ADR-005 질문 4와 같은 방식).  
  사본은 찍은 화면과 설명을 올립니다. 검토하는 동안에는 파일을 고치지 않고, 검토가 끝나면 의견을 옮기고 바뀐 곳을 보여 줍니다.

**6. 지킬 것**

- 참고에서 로고, 회사·서비스 이름, 캐릭터·사진·그림, 문구, 사이트의 코드와 CSS 파일을 가져오지 않습니다.  
  참고 캡처와 찍은 화면은 `_raw/design/`(git 밖)에만 둡니다.
- 공개된 웹 사이트는 주소와 본 날을 근거로 적을 수 있습니다.  
  내부 화면(그룹웨어 등)은 이름도 적지 않고 "내부 업무 화면 캡처"처럼 일반 이름으로 적습니다(저장소 규칙).
- 시안의 데이터는 모두 가상입니다. 실제 고객 정보, 실제 장애 사례, 실제 상품 이름을 쓰지 않습니다(저장소 규칙, 요건 0-22).
- 값(색, 크기)마다 근거를 적습니다. 근거 없는 값은 짐작으로 채우지 않습니다(저장소 규칙).
- 요건에서 정한 답을 다시 정하지 않습니다. 고쳐야 하면 요건정리로 되돌려 보냅니다.
- 사람이 읽는 문서이므로 업무 말로 씁니다. 디자인 용어(대비, 토큰 등)는 처음 나올 때 무엇인지 한 줄로 풉니다.

**7. 다음 단계로 넘기기**

- 화면 규칙과 탭 하나의 시안이 확정되면, 그 탭은 스펙(`/sdd-spec-writer`)으로 넘어갈 수 있다고 알려 줍니다.  
  스펙은 아키텍처 승인(③)도 끝나야 확정할 수 있으므로 아키텍처 상태도 함께 알립니다. 아직 만들지 않은 에이전트면 그렇다고 알립니다.
- 구현 계획에 넘기는 것을 「다른 단계로 넘길 것」에 적습니다.  
  `tokens.css`를 `app/globals.css`로 옮겨 값이 실제로 바뀌는지 확인하기, 기본 틀을 앱 뼈대로 쓴다는 전제로 썼다는 것입니다.  
  구현 계획이 기본 틀을 쓰지 않기로 하면 디자인으로 되돌려 보냅니다.

| 1 | `requirements.md`가 없을 때 부릅니다. | 시작하지 않고, 이유와 요건정리(`/sdd-analyst`)를 안내합니다.<br>파일을 만들지 않습니다. |
| 2 | 처음 부릅니다. 요건 파일 몇 개가 작성 중입니다. | 요건 파일마다 상태를 보여 주고 "확정은 요건이 모두 확정된 뒤"라고 알립니다.<br>처음 묻는 것이 참고 디자인입니다(웹 주소, 캡처, 말, 없음). 이때는 파일을 만들지 않습니다. |
| 3 | 공개 웹 주소 하나를 주고 "색과 분위기가 좋다"고 말합니다. | 에이전트가 찍은 화면을 보고 「가져올 것 / 가져오지 않을 것」 표를 보여 줍니다.<br>로고, 이름, 그림, 문구는 「가져오지 않을 것」에 있습니다. 찍은 화면은 `_raw/design/`에만 있습니다. |
| 4 | 첫 화면에 팝업이 뜨는 주소를 줍니다. | 팝업이 가린다고 말하고, 가림막 아래에서 뽑은 색을 그대로 쓰지 않습니다. |
| 5 | 로그인해야 보이는 주소와, 사내 화면 캡처(가상으로 만든 것)를 줍니다. | 로그인 화면은 내용을 짐작하지 않고 캡처를 부탁합니다.<br>사내 화면의 이름, 메뉴 이름, 화면 속 정보가 `docs/` 어디에도 없고, "내부 업무 화면 캡처"처럼 일반 이름으로 적힙니다. |
| 6 | 참고 없이 "알아서 해 줘"라고 합니다. | 기본 틀의 디자인으로 시작하고, 근거를 "기본 틀의 기본값"으로 적습니다. 짐작한 값이 없습니다. |
| 7 | 화면 규칙의 색 장 초안을 받습니다. | 색마다 의미 이름, 값, 기본 틀의 이름, 쓰는 곳, 근거가 있습니다. 등급(P1~P4)과 처리 상태의 색에 요건 번호가 있습니다.<br>글자와 바탕의 대비 확인 결과가 있고, 견본을 찍은 화면이 함께 보입니다. `tokens.css`의 값이 표와 같습니다. |
| 8 | 탭 1(상담등록)의 시안을 받습니다. | 설명의 영역마다 요건 번호가 있고, 요건에 없는 정보가 없습니다.<br>AI 진행 단계(1-06)의 모양과 불러오는 중, 빈 화면, 오류 모양이 있습니다.<br>HTML이 브라우저에서 열리고, 같은 이름의 찍은 화면이 있습니다. 데이터는 모두 가상입니다. |
| 9 | 시안을 보다가 "줄을 누르면 상세가 열리게 해 줘", "고객 전화번호도 보여 줘"라고 합니다. | 누르면 어떻게 되나는 스펙으로 「다른 단계로 넘길 것」에 적힙니다.<br>요건에 없는 전화번호는 넣지 않고, 요건정리로 되돌려 보내야 한다고 알립니다. |
| 10 | 시안을 쓴 뒤 탭 하나의 요건을 고쳐 커밋하고 부릅니다. | 다른 일보다 먼저 바뀐 요건 번호와 걸리는 시안을 표로 보여 줍니다.<br>걸리는 시안만 고치고, 「읽은 것」의 그 파일 커밋이 새것으로 바뀝니다. |
| 11 | 화면 규칙의 강조색 값만 바꿉니다. | 모든 시안이 새 색으로 바뀌고, 찍은 화면을 다시 찍습니다. 시안의 상태는 그대로입니다. |
| 12 | 요건이 모두 확정된 뒤, 화면 규칙과 탭 1 시안을 승인했다고 말합니다. | 둘이 확정되고 승인 칸이 채워집니다.<br>탭 1은 스펙으로 넘어갈 수 있다고 알리고, 아키텍처 상태도 알립니다. 화면 규칙이 확인 대기면 시안은 확정하지 않습니다. |

## 주의할 점

- 기본 틀의 지침(`AGENTS.md`)은 "색을 직접 바꾸지 마세요"라고 합니다. 화면 코드에 색을 직접 쓰지 말라는 뜻으로 읽었고, 질문 2의 안 가는 색 값을 `app/globals.css` 한곳에서만 바꿉니다.  
  패키지를 설치해 실제로 바뀌는지는 구현 계획에서 확인합니다. 안 되면 디자인으로 되돌려 보내 질문 2를 다시 봅니다.
- 시안은 실제 부품으로 그린 것이 아니라서, 구현된 화면과 모양이 조금 다를 수 있습니다. ⑦ 화면 확인에서 시안과 비교합니다.
- 웹 주소를 찍는 방법은 이 PC(Windows, Chrome)에서 시험했습니다. 다른 PC에서 브라우저를 찾지 못하면 사람에게 캡처를 부탁합니다.
- 찍은 화면(`.png`)을 git에 올리므로 저장소가 조금 커집니다. 탭이 7개라 괜찮다고 봤습니다.
- 마감(10/30)이 짧아 탭 7개의 시안을 모두 만들기 어려울 수 있습니다. 어느 탭을 시안 없이 화면 규칙만으로 만들지는 구동할 때 사람이 정합니다.  
  그렇게 정한 탭은 ADR-002 ④("그 탭의 시안을 승인해야 스펙을 씀")와 어긋나므로, 시안 설명에 "시안 생략"과 이유를 적고 확정합니다.
