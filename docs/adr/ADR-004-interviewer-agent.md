# ADR-004 인터뷰 에이전트

- 상태: 채택
- 날짜: 2026-10-23

## 요약

인터뷰는 요건정의를 하기 전에, 만들려는 것에 대한 이해도를 높이는 단계입니다.  
하려는 것을 먼저 묻고, 참고 자료를 읽어 애매한 곳으로 질문지를 만들어 묻습니다.  
질문과 답은 `scope.md`에 기록하고, 사람이 확인하면 확정됩니다(① 범위 확인).  
요건정리는 확정된 `scope.md`를 읽고 시작합니다.

```
하려는 것을 묻는다 (주제, 목적, 자세한 내용)
  ↓
참고 자료를 받아 읽는다 (링크는 적어 두고, 파일은 _raw/에)
  ↓
애매한 곳, 궁금한 곳, 자료끼리 다른 곳으로 질문지를 만든다 (추천 답을 채워 둠)
  ↓
질문지를 보여 주고 빠진 것과 뺄 것을 확인받는다 → scope.md를 만든다 (작성 중)
  ↓
하나씩 묻거나, 표로 한 번에 보여 주고 답을 받는다 (답마다 scope.md에 옮김)
  ↓
확인을 요청한다 (확인 대기) → 사람이 확인하면 확정 → 요건정리로
```

`scope.md`는 미리 정한 칸 없이, 질문과 답의 기록으로 남깁니다.

| 순서 | 담는 것 |
|---|---|
| 상태와 확인 | 작성 중 → 확인 대기 → 확정, 확인한 사람과 날짜 |
| 참고 자료 | 자료 이름과 위치 (링크 또는 `_raw/` 안의 경로) |
| 정리 | 무엇을 만드나 3~5줄 |
| 1. 하려는 것 | 질문, 고른 답, 고르지 않은 안, 이유 |
| 2. 참고 자료에서 확인한 것 | 질문, 근거 자료, 고른 답, 고르지 않은 안, 이유<br>묻지 않고 자료로 확인한 것도 범위에 영향이 있으면 적음 |
| 3. 미룬 것과 뺀 것 | 항목, 미룸/뺌, 이유 |
| 4. 질문 대기 | 인터뷰에서 물을 것: 확인, 질문, 추천 답, 다른 안, 근거, 의견, 갈래<br>다른 단계로 넘길 것: 질문, 넘길 단계 |

- 인터뷰는 요건을 쓰지 않습니다. 세부 요건은 요건정리로 넘깁니다.
- 시험 장면은 7개이고, 「결정」 8번에 있습니다.

자세한 내용은 아래 「결정」에 있습니다.

## 배경

ADR-002에서 정한 개발 에이전트 10개 가운데 첫 번째인 인터뷰 에이전트(`sdd-interviewer`)를 만듭니다.  
ADR-003의 만드는 순서에서 첫 단계(에이전트 ADR 쓰기)에 해당합니다.  
그래서 이 ADR을 쓰면서 ADR-003의 방식이 실제로 맞는지도 처음 시험합니다.

인터뷰는 요건정의를 하기 전에, 만들려는 것에 대한 이해도를 높이기 위해 합니다.  
이해도가 높아야 요건정의를 정확하게 할 수 있습니다.

지금 상태에서 공유된 자료만 보고 바로 요건을 쓰면 안 되는 이유가 있습니다.  
지금 가진 자료(v2 요건정의서, 팀 회의 기록)끼리 서로 다른 말을 하는 곳이 있기 때문입니다.  
예를 들어 v2 요건정의서는 관리자 승인 단계를 뺐지만, 3차 회의에서는 넣을지 다시 보기로 했습니다.

그래서 인터뷰에서는 하려는 것과 참고 자료를 질문으로 하나씩 확인합니다.  
질문과 답을 기록으로 남기고, 요건정리는 그 기록을 읽고 시작합니다.

## 정할 것

ADR-003의 「에이전트 ADR에 쓸 것」 8가지를 정합니다.

| 항목 | 무엇을 정하나 | 지금 아는 것 |
|---|---|---|
| 1. 하는 일 | 인터뷰가 하는 것과 하지 않는 것 | 이해도를 높이는 것까지 하고, 요건을 쓰지는 않음 (배경) |
| 2. 읽는 것 | 묻기 전에 읽을 자료 | **질문 2**<br>우리 프로젝트에서는 드라이브의 v2 설계서를 비롯한 자료 전부, 필요하면 구현 코드. v1은 보지 않음 (HANDOFF) |
| 3. 남기는 것 | `scope.md`의 모양 | **질문 1** |
| 4. 대화 순서 | 무엇부터, 어떻게 묻나 | **질문 2** |
| 5. 사람 확인 | 누가 확정하나 | 팀이 확인할지는 아직 정하지 않음 |
| 6. 지킬 것 | 하면 안 되는 것 | 실제 고객 정보, 실제 장애 사례, 사내 시스템 이름은 `scope.md`에 넣지 않음 (저장소 규칙) |
| 7. 다음 단계로 넘기기 | 요건정리가 무엇을 이어받나 | 확정된 `scope.md`만 넘김 (ADR-003 약속) |
| 8. 시험 장면 | 3개 이상, 각각 무엇이 나오면 통과인지 | 아직 정하지 않음 |

먼저 두 가지를 정합니다.

- **질문 1. `scope.md`를 어떤 모양으로 남기나** (3번 남기는 것)
- **질문 2. 어떻게 묻나** (2번 읽는 것, 4번 대화 순서)

이 둘이 정해지면 나머지(사람 확인, 다음 단계로 넘기기, 시험 장면)가 따라옵니다.

## 질문 1. `scope.md`를 어떤 모양으로 남기나

### 지켜야 할 조건

1. 미리 정한 틀을 깔지 않습니다.  
   인터뷰를 시작할 때는 무엇을 만들지 아직 잘 모릅니다. 화면 탭이 있는지도 모릅니다.
2. 모든 결정에 이유와 고르지 않은 안이 남습니다.  
   나중에 "이거 왜 이렇게 했지?"를 바로 찾을 수 있어야 합니다.
3. 요건정리가 읽고 바로 시작할 수 있습니다.
4. 인터뷰와 요건정리가 같은 일을 하지 않습니다.  
   인터뷰는 이해도를 높이고, 요건정리는 요건을 씁니다.

### 안 1. 정해진 칸을 미리 두기

범위, 화면 탭 목록, 큰 갈림길처럼 칸을 미리 정해 두고, 인터뷰에서 그 칸을 채웁니다.

| 구분 | 내용 |
|---|---|
| 장점 | 어떤 일이든 같은 모양으로 남아서 읽기 쉽습니다. |
| 단점 | 화면 탭처럼 미리 정한 틀을 깔고 시작합니다.<br>칸에 맞지 않는 내용은 빠지기 쉽습니다.<br>결정마다 이유가 남는지는 칸마다 다릅니다. |
| 결과 | 조건 3과 4는 지킵니다.<br>조건 1은 지키지 못하고, 조건 2는 일부만 지킵니다. |

### 안 2. 질문과 답을 기록하기

하려는 것과 참고 자료를 질문으로 확인하고, 질문마다 고른 답, 고르지 않은 안, 이유를 표로 남깁니다.

| 구분 | 내용 |
|---|---|
| 장점 | 미리 정한 틀이 없어서 어떤 일에도 쓸 수 있습니다.<br>모든 결정에 이유와 고르지 않은 안이 남습니다.<br>요건정리는 이 표를 읽고 바로 시작할 수 있습니다. |
| 단점 | 무엇을 만들기로 했는지가 표 여러 줄에 흩어집니다.<br>그래서 맨 위에 "정리" 몇 줄을 둬서 보완합니다. |
| 결과 | 네 조건을 모두 지킵니다. |

### 안 3. 질문과 답 + 요건 초안

안 2에 더해, 답을 바탕으로 요건 초안까지 씁니다.

| 구분 | 내용 |
|---|---|
| 장점 | 요건정리가 할 일이 줄어듭니다. |
| 단점 | 요건정리와 일이 겹칩니다.<br>인터뷰가 길어지고, 확인할 양도 많아집니다. |
| 결과 | 조건 1~3은 지킵니다.<br>조건 4는 지키지 못합니다. |

## 질문 2. 어떻게 묻나

### 지켜야 할 조건

1. 자료에 이미 답이 있는 것은 다시 묻지 않습니다(ADR-003 약속).
2. 하려는 것(주제, 목적, 자세한 내용)은 자료가 없어도 꼭 묻습니다.
3. 우리 자료에만 맞춘 질문이 아니라서, 다른 일에도 쓸 수 있습니다.
4. 사람이 편한 방식으로 답할 수 있습니다.

### 안 A. 정해진 질문지로 묻기

미리 정해 둔 질문 몇 개를 매번 같은 순서로 묻습니다.  
예전에 쓰던 SDD 도구의 방식입니다.

| 구분 | 내용 |
|---|---|
| 장점 | 매번 같은 것을 물어서 빠뜨리는 것이 적습니다. |
| 단점 | 자료에 이미 답이 있어도 묻습니다.<br>자료끼리 말이 다른 곳(우리의 관리자 승인 단계, 심각도 기준)을 따로 찾아 묻지 못합니다. |
| 결과 | 조건 2와 3은 지킵니다.<br>조건 1은 지키지 못합니다. |

### 안 B. 자료만 읽고 질문지를 만들어 묻기

참고 자료를 먼저 받아 읽고, 애매한 곳과 궁금한 곳으로 질문지를 만들어 묻습니다.

| 구분 | 내용 |
|---|---|
| 장점 | 자료를 보고 모르는 것만 묻습니다.<br>자료끼리 말이 다른 곳이 질문으로 올라옵니다. |
| 단점 | 자료에 없는 것은 묻지 않게 됩니다.<br>하려는 것(주제, 목적)을 자료에서 짐작하게 됩니다. |
| 결과 | 조건 1과 3은 지킵니다.<br>조건 2는 지키지 못합니다. |

### 안 C. 하려는 것부터 묻고, 자료로 질문지를 만들어 묻기

```
1. 하려는 것을 묻는다 (주제, 목적, 자세한 내용)
  ↓
2. 참고 자료를 받는다 (링크 또는 파일)
  ↓
3. 자료를 읽고 질문지를 만든다
   - 자료에서 애매한 곳, 궁금한 곳, 자료끼리 다른 곳
   - 질문마다 자료에서 찾은 추천 답을 미리 채워 둠
  ↓
4. 질문지를 보여 주고, 빠진 것과 뺄 것을 확인받는다 → scope.md를 만든다 (작성 중)
  ↓
5. 묻는 방식을 고른다
   - 하나씩 묻고 답하기
   - 표로 한 번에 보여 주고 답 받기
  ↓
6. 답을 scope.md에 옮기고 확인을 요청한다 (확인 대기)
```

| 구분 | 내용 |
|---|---|
| 장점 | 하려는 것을 자료에서 짐작하지 않고 사람에게 직접 묻습니다.<br>자료를 보고 모르는 것만 묻습니다.<br>묻기 전에 질문지를 보고 고칠 수 있습니다.<br>하나씩 답할지, 표로 한 번에 답할지 사람이 고릅니다. |
| 단점 | 질문지를 확인하는 차례가 하나 늘어납니다. |
| 결과 | 네 조건을 모두 지킵니다. |

## 어느 안을 고르든 넣을 것

- **인터뷰에서 정하지 않을 것은 넘길 단계를 적습니다.**  
  예: 세부 요건은 요건정리로, 데이터와 시스템 연결은 아키텍처로, 화면 모양은 디자인으로 넘깁니다.  
  인터뷰 중에 이런 이야기가 나오면 정하지 않고, 넘길 단계와 함께 질문 대기에 적어 둡니다.
- **참고 자료는 링크면 링크를 적고, 파일이면 `_raw/`에 둡니다.**  
  `_raw/`는 `.gitignore`에 이미 "원본 자료 보관용 (git 밖)"으로 잡혀 있는 폴더라 git에 올라가지 않습니다.  
  자료 속의 실제 정보는 `scope.md`에 옮기지 않습니다.

## 결정

질문 1은 안 2(질문과 답을 기록하기), 질문 2는 안 C(하려는 것부터 묻고, 자료로 질문지를 만들어 묻기)로 정했습니다.  
각 질문에서 조건을 모두 지키는 안은 이 둘뿐입니다.

아래는 ADR-003의 「에이전트 ADR에 쓸 것」 8가지 순서입니다.

**1. 하는 일**

- 하는 일: 요건정의를 하기 전에, 하려는 것과 참고 자료를 질문으로 확인해 이해도를 높입니다.
- 하지 않는 일: 요건을 쓰지 않습니다.  
  세부 요건은 요건정리로, 데이터와 시스템 연결은 아키텍처로, 화면 모양은 디자인으로 넘깁니다.  
  인터뷰 중에 이런 이야기가 나오면 정하지 않고, 질문 대기의 「다른 단계로 넘길 것」에 넘길 단계와 함께 적습니다.

**2. 읽는 것**

- 사람이 알려 준 참고 자료를 읽습니다. 자료는 링크나 파일로 받습니다.
- 링크면 참고 자료 목록에 링크를 적고 읽습니다. 내려받을 수 있으면 `_raw/`에 내려받아 둡니다.
- 파일이면 `_raw/`에 옮겨 둡니다. `_raw/`가 없으면 만듭니다.
- 읽거나 내려받을 수 없으면, 파일을 `_raw/`에 넣는 방법을 안내합니다.
- 우리 프로젝트에서는 드라이브의 v2 설계서를 비롯한 자료 전부이고, 필요하면 구현 코드도 읽습니다. v1은 보지 않습니다.  
  이 내용은 설명서에 적지 않고, 구동할 때 사람이 알려 줍니다.  
  설명서는 다른 일에도 쓸 수 있게 둡니다(질문 2의 조건 3).

**3. 남기는 것**

- `docs/requirements/scope.md` 하나를 남깁니다. 모양은 위 「안 2로 하면 `scope.md`는 이런 모양입니다」를 따릅니다.
- 맨 위에 참고 자료 목록(이름과 위치)을 둡니다. 요건정리도 이 목록의 자료를 읽습니다.
- 자료에 답이 있어서 묻지 않은 것 가운데 범위에 영향이 있는 것은 2번 표에 "자료로 확인(묻지 않음)"으로 적습니다.
- 질문지를 확인받으면 바로 `scope.md`를 "작성 중"으로 만듭니다.  
  질문지는 질문 대기의 「인터뷰에서 물을 것」에 확인, 추천 답, 다른 안, 근거, 의견, 갈래와 함께 그대로 옮깁니다.  
  답을 받을 때마다 그 질문을 1번이나 2번 표로 옮깁니다.  
  대화가 끊기거나, 길어져서 앞 내용이 줄어도 답이 남게 하기 위해서입니다.
- 추천 답과 근거까지 남기는 것은, 팀이 노션 같은 곳에서 질문지를 검토한 뒤 git에 다시 옮길 때 내용이 빠지지 않게 하기 위해서입니다(2026-10-23 구동에서 고침).
- 맨 위에 "요건정리는 여기서 정한 답을 다시 정하지 않고, 고쳐야 하면 인터뷰로 되돌려 보낸다"는 안내를 둡니다.
- 양식 파일은 `.claude/skills/sdd-interviewer/template.md`에 둡니다(ADR-003).

**4. 대화 순서**

- 위 「요약」의 흐름을 따릅니다.
- 시작할 때 무엇을 하고 무엇은 하지 않는지 짧게 알립니다.
- `scope.md`가 이미 있으면 상태를 보고 나눕니다.
  - 작성 중: 이어서 할지 묻습니다.
  - 확인 대기: 확정할지, 고칠 곳이 있는지 묻습니다.
  - 확정: 무엇을 고칠지 묻고, 고치면 확인 대기로 되돌립니다. 요건정리가 되돌려 보낸 경우도 여기로 옵니다.
- 질문지에 무엇을 올릴지는 따로 정하지 않고, 하려는 것과 자료를 보고 AI가 판단합니다.
- 질문지는 `scope.md`의 「인터뷰에서 물을 것」과 같은 모양(확인, 번호, 질문, 추천 답, 다른 안, 근거, 의견, 갈래)으로 보여 줍니다.
- 질문지에는 질문마다 자료에서 찾은 추천 답을 채워 둡니다. 근거가 없으면 "추천 없음"으로 둡니다.
- 추천 답은 문장으로 끝내고, 추천하는 이유는 "(이유: …)"로 따로 적습니다. 인터뷰한 사람만 아는 말과 낯선 줄임말은 풀어 씁니다(2026-10-23 구동에서 더함).
- 하나씩 물을 때는 질문 도구가 받는 대로 한 번에 4개까지 묻습니다.
- 답하다가 새 질문이 생기면 「인터뷰에서 물을 것」 끝에 붙여 같은 방식으로 묻습니다.

**5. 사람 확인**

- 다 묻고 「정리」를 쓰면 상태를 "확인 대기"로 바꾸고 확인을 요청합니다.
- 확인은 인터뷰를 한 사람이 해도 되고, 팀원이 해도 됩니다. 확인한 사람과 날짜를 확인 칸에 적습니다.
- 사람이 확인하면 상태를 "확정"으로 바꿉니다. 흐름에서는 ① 범위 확인입니다(ADR-002).
- 사람이 확인했다고 말하기 전에는 확정으로 바꾸지 않습니다.

**6. 지킬 것**

- 자료에 이미 답이 있는 것은 다시 묻지 않습니다.
- 근거가 없는 것은 짐작으로 채우지 않고 질문 대기로 남깁니다.
- 실제 고객 정보, 실제 장애 사례, 사내 시스템 이름은 `scope.md`에 넣지 않습니다(저장소 규칙).  
  자료 이름이나 링크에 들어 있어도 같고, 일반 이름으로 바꿔 적습니다.

**7. 다음 단계로 넘기기**

- 확정되면 다음은 요건정리(`/sdd-analyst`)라고 알려 줍니다.
- 요건정리는 확정된 `scope.md`와 거기 적힌 참고 자료를 읽고 시작합니다(ADR-003 약속).

**8. 시험 장면**

장면 3, 5는 가상 자료를 만들어 씁니다.  
가상 자료는 `_raw/test/`에 두고 git에 올리지 않습니다.

| # | 장면 | 통과 |
|---|---|---|
| 1 | 자료 없이 부릅니다. | 첫 질문이 하려는 것(주제, 목적, 자세한 내용)입니다.<br>빈 곳을 짐작으로 채우지 않고 질문 대기로 남깁니다. |
| 2 | v2 요건정의서와 회의 기록을 줍니다. | 관리자 승인 단계와 심각도 기준이 "자료끼리 다름"으로 질문지에 오르고, 근거 자료가 둘 다 적힙니다. |
| 3 | 자료에 이미 답이 있는 내용이 있습니다. | 그 내용은 질문지에 오르지 않습니다.<br>범위에 영향이 있으면 2번 표에 "자료로 확인(묻지 않음)"으로 적힙니다. |
| 4 | 답하다가 화면 모양이나 세부 요건 이야기를 꺼냅니다. | 그 자리에서 정하지 않고, 넘길 단계(디자인, 요건정리)와 함께 「다른 단계로 넘길 것」에 적힙니다. |
| 5 | 가상의 사내 시스템 이름과 고객 정보가 든 자료를 줍니다. | `scope.md`에 그 이름과 고객 정보가 없고, 일반 이름으로 바뀌어 있습니다. |
| 6 | 다 쓴 뒤 확인했다고 말합니다. | 상태가 확인 대기에서 확정으로 바뀌고, 확인 칸에 확인한 사람과 날짜가 적힙니다.<br>그 전에는 확정으로 바꾸지 않습니다.<br>마지막에 다음 단계(`/sdd-analyst`)를 알려 줍니다. |

## 참고: 예전에 쓰던 SDD 도구와 비교

인터뷰 단계만 비교했습니다.  
그 도구는 구조만 참고했고 문장은 가져오지 않았습니다.

| | 우리 (추천안) | 예전에 쓰던 SDD 도구 |
|---|---|---|
| 순서 | 인터뷰 → 요건정리 | 인터뷰 → 요구 문서 (같음) |
| 언제 하나 | 항상 | 일이 클 때만 |
| 목적 | 요건정의 전에 이해도를 높임 | 큰 일을 기능 묶음으로 나눔 |
| 세부 요건 | 묻지 않고 요건정리로 넘김 | 묻지 않고, 넘길 단계를 항목마다 정해 둠 |
| 묻는 방식 | 하려는 것부터 묻고, 자료로 질문지를 만듦 | 정해진 질문 몇 개 + 나중에 되돌리기 어려운 개발 질문 몇 개 |
| 남기는 것 | `scope.md` 하나 (질문과 답의 기록) | 회차 문서, 미룬 것 목록, 기능 묶음마다 입력 문서 |

가져온 생각은 세 가지입니다.

- 인터뷰에서 정하지 않을 것은 넘길 단계를 적습니다.
- 미룬 것과 그 이유, 고르지 않은 안을 남깁니다.
- 다음 단계가 다시 정하면 안 된다는 것을 문서에 표시합니다.
