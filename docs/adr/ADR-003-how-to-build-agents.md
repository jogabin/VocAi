# ADR-003 에이전트를 만드는 방식

- 상태: 검토 중
- 날짜: 2026-10-23 (처음 작성: 2026-10-21)

## 요약

개발 에이전트 10개를 만들 때 따를 표준으로 세 가지(만드는 순서, 에이전트끼리 지킬 약속, 둘 곳과 이름)를 정했습니다.  
아직 검토 중이며, 인터뷰 에이전트를 이 방식으로 만들어 본 뒤 채택할 예정입니다.

**1. 만드는 순서** (에이전트 하나마다)

```
에이전트 ADR 쓰기
  ↓
시험 장면 3개 이상 정하기 (무엇이 나오면 통과인지)
  ↓
설명서와 양식 쓰기
  ↓
실제로 구동하고 사람이 결과 확인
  ↓
통과하지 못한 곳을 고치고 다시 구동 → 통과하면 커밋
```

에이전트 ADR은 모두 같은 순서로 씁니다.  
하는 일, 읽는 것, 남기는 것, 대화 순서, 사람 확인, 지킬 것, 다음 단계로 넘기기, 시험 장면입니다.

**2. 에이전트끼리 지킬 약속**

| 약속 | 내용 |
|---|---|
| 공통 규칙은 한곳에 | 묻는 방식처럼 모든 에이전트가 지킬 규칙은 `.claude/rules/sdd.md`에 둡니다. 세션이 열리면 자동으로 읽힙니다. |
| 문서 상태 | 에이전트가 남기는 문서 맨 위에 상태를 적습니다. 작성 중 → 확인 대기 → 확정 |
| 확정은 앞 단계 확정 뒤 | 앞 단계 문서가 확정되기 전에도 초안은 쓸 수 있습니다. 내 문서의 확정은 읽은 앞 단계 문서가 모두 확정된 뒤에만 합니다(2026-10-24에 바꿈, ADR-006). |
| 되돌려 보내기 | 앞 단계 문서에서 문제를 찾으면 직접 고치지 않고, 그 문서를 만든 단계로 되돌려 보냅니다. |
| 바뀐 곳만 다시 보기 | 앞 단계 문서가 읽은 때의 커밋 뒤에 바뀌면, 비교해 걸리는 곳만 고칩니다(2026-10-23에 더함, 2026-10-24에 바꿈). |

단계 사이는 모두 이렇게 이어집니다. 인터뷰에서 요건정리로 넘어가는 예를 들면 이렇습니다.

```
인터뷰 에이전트가 scope.md를 씀 (작성 중)
  ↓ 다 쓰면
사람에게 확인을 요청함 (확인 대기)
  ↓ 사람이 확인하면
scope.md가 확정됨 (확정)
  ↓
요건정리 에이전트가 확정된 scope.md만 읽고 시작함
  ↓ scope.md에서 문제를 찾으면
고치지 않고 인터뷰로 되돌려 보냄
```

요건정리는 범위가 확정되어야 시작합니다(ADR-005).  
아키텍처부터는 앞 단계가 확정되기 전에 초안을 먼저 쓰고, 확정만 앞 단계 확정 뒤에 할 수 있습니다(ADR-006).

**3. 둘 곳과 이름**

```
.claude/
├── rules/sdd.md        에이전트끼리 지킬 약속
├── skills/sdd-*/       대화형 6개 (사람이 /sdd-interviewer 처럼 부름)
└── agents/sdd/*.md     실행형 4개 (Claude가 sdd-tester 처럼 이름으로 맡김)
```

- 플러그인으로 묶지 않고 `.claude/`에 둡니다. 플러그인은 약속을 늘 읽히게 하기 어렵고, 실행형 에이전트 설정 일부가 무시되기 때문입니다.
- 이름은 맡은 역할로 짓고 앞에 `sdd-`를 붙입니다. 10개 이름은 아래 「에이전트 이름」 표에 있습니다.

다섯 안 가운데 안 3(공식 방식에 에이전트끼리의 약속만 더하기)을 골랐습니다.  
자세한 내용은 아래 「결정」에 있습니다.

## 배경

ADR-002에서 개발 에이전트 10개를 정했습니다.  
하나씩 만들기 전에, 모든 에이전트에 똑같이 적용할 만드는 방식을 먼저 정합니다.

방식 없이 만들면 에이전트마다 묻는 방식도, 문서를 넘기는 방식도 달라집니다.  
나중에 만든 에이전트에 맞춰 방식을 바꾸면, 먼저 만든 에이전트도 다시 고쳐야 합니다.

정할 것은 세 가지입니다.

- 만드는 절차: 에이전트 하나를 어떤 순서로 만들고, 어떻게 시험하는가
- 에이전트 사이의 약속: 여러 에이전트가 똑같이 지켜야 하는 것은 무엇인가
- 둘 곳: 에이전트 설명서와 공통 규칙을 어느 폴더에, 어떤 이름으로 두는가

참고한 자료는 Claude Code 공식 문서와, 예전에 쓰던 스펙 주도 개발(SDD) 도구입니다.  
SDD 도구는 구조만 참고했고 문장은 가져오지 않았습니다.  
실행형 에이전트에만 해당하는 것(보고 형식, 작업 공간 나누기 등)은 실행형을 만들 때 정합니다.

이 문서에서 "에이전트 설명서"는 Claude가 읽고 따르는 파일을 말합니다.  
대화형은 `.claude/skills/<이름>/SKILL.md`, 실행형은 `.claude/agents/<이름>.md`입니다.

## 지켜야 할 조건

1. Claude Code가 공식으로 권하는 방식을 참고합니다.
2. 에이전트 사이의 약속은 모든 에이전트가 같습니다.  
   묻는 방식, 앞 단계 문서를 넘겨받는 방식처럼 여러 에이전트에 걸친 규칙을 말합니다.
3. 여러 에이전트에 공통인 규칙은 한곳에만 둡니다.
4. 에이전트 설명서가 짧습니다.  
   공식 문서는 스킬 파일(`SKILL.md`)을 500줄 이하로 두라고 권합니다.
5. 앞 단계가 남긴 문서를 다음 단계 에이전트가 그대로 이어받습니다.
6. 만든 에이전트는 실제로 구동해 보고 확인합니다.
7. 에이전트 설명서는 그 에이전트가 하는 일에 맞게 씁니다.

## 검토한 안

### 안 1. Claude Code 공식 방식 그대로

공식 문서가 정해 주는 것만 따르고, 나머지는 에이전트마다 알아서 씁니다.

| 공식 문서가 정해 주는 것 | 정해 주지 않는 것 |
|---|---|
| 설명서를 두는 자리 | 설명서 안의 목차와 내용 |
| 설명서 머리에 적을 정보 (이름, 무엇을 하고 언제 쓰는지 등) | 여러 에이전트가 같이 지킬 규칙을 둘 자리 |
| 작성 요령 (500줄 이하, 길면 다른 파일로 빼기) | 남기는 문서의 모양 |
| 만드는 순서 (시험 장면 먼저) | 앞 단계 문서를 다음 단계가 넘겨받는 방식 |

```
.claude/skills/
├── interviewer/
│   └── SKILL.md          인터뷰 에이전트 설명서
└── analyst/
    └── SKILL.md          요건정리 에이전트 설명서

docs/requirements/
├── scope.md              모양은 인터뷰 에이전트가 정함
└── requirements.md       모양은 요건정리 에이전트가 정함
```

폴더와 파일 이름은 예시입니다.

공식 문서가 권하는 만드는 순서는 이렇습니다.

1. 에이전트가 해내야 할 시험 장면을 3개 이상 먼저 정합니다.  
   예: "v2 자료를 주고 대화하면, 화면 탭 목록이 담긴 범위 문서가 나온다"
2. 그 장면을 통과하는 데 필요한 만큼만 지침을 씁니다.
3. 실제로 구동해 보고, 통과하지 못한 곳을 고칩니다.

| 구분 | 내용 |
|---|---|
| 장점 | 도구가 권하는 그대로라 어긋날 일이 없습니다.<br>설명서를 일에 맞게 짧게 쓰고, 시험 장면으로 확인하는 절차가 들어 있습니다. |
| 단점 | 요건정리 에이전트는 `scope.md`를 사람이 확인했는지 알 수 없습니다. 반쯤 쓴 범위로 시작할 수 있습니다.<br>묻는 방식이 에이전트마다 달라질 수 있습니다. 같게 하려면 같은 규칙을 설명서마다 되풀이해 써야 합니다. |
| 결과 | 조건 1, 4, 6, 7은 지킵니다.<br>에이전트 사이의 약속이 없어서 조건 2와 5는 지키지 못합니다. |

### 안 2. 스펙 주도 개발(SDD) 도구 방식 그대로

설명서 하나에 규칙, 단계별 절차, 문서 규격, 예시까지 모두 담습니다.  
남길 문서의 양식과 다 쓴 예시는 같은 폴더에 따로 둡니다.

```
.claude/skills/interviewer/
├── SKILL.md       규칙, 절차, 문서 규격, 예시를 모두 담음
├── template.md    남길 문서의 양식
└── sample.md      다 쓴 예시
```

단계 사이는 이렇게 잇습니다.

- 기능마다 폴더를 만들고, 그 안에 "다음에 부를 단계와 넘겨줄 파일"을 적은 파일을 둡니다.
- 한 단계가 끝나면 대화를 비우고, 그 파일을 보고 다음 단계를 부릅니다.
- 단계마다 사람에게 확인받고, 문서를 검토하는 에이전트가 따로 있습니다.

| 구분 | 내용 |
|---|---|
| 장점 | 빠뜨리는 것이 적습니다.<br>단계 사이가 촘촘하게 이어지고, 양식과 예시가 있어서 문서 모양이 일정합니다. |
| 단점 | 설명서 하나가 길면 1,400줄이 넘습니다(파일을 직접 세어 봄). 공식 권장 길이(500줄)의 세 배 가까이 됩니다.<br>진행률 파일, 상태 표시줄, 단계 잇기 파일처럼 관리할 부속 장치가 많습니다. 그 도구의 안내 문서에 적힌 스킬과 에이전트 수가 이미 실제와 다를 정도입니다.<br>여러 팀이 큰 제품을 만드는 데 맞춘 방식이라 앱 하나에는 무겁습니다. |
| 결과 | 조건 2, 3, 5는 지킵니다.<br>설명서가 길어서 조건 4를 지키지 못하고, 공식 권장과도 멀어집니다(조건 1).<br>큰 설명서들이 같은 무거운 틀을 따라서, 일에 맞게 쓰기도 어렵습니다(조건 7). |

### 안 3. 공식 방식에 에이전트 사이의 약속만 더하기

안 1을 그대로 두고, 여러 에이전트에 걸친 약속만 더합니다.  
설명서 안의 목차와 내용은 안 1처럼 에이전트마다 하는 일에 맞게 씁니다.

```
.claude/
├── rules/
│   └── sdd.md                    에이전트 사이의 약속 (세션이 열리면 자동으로 읽힘)
└── skills/
    ├── sdd-interviewer/
    │   ├── SKILL.md              인터뷰 에이전트 설명서 (일에 맞게 씀)
    │   └── template.md           scope.md의 빈 양식
    └── sdd-analyst/
        ├── SKILL.md              요건정리 에이전트 설명서 (일에 맞게 씀)
        └── template.md           requirements.md의 빈 양식

docs/requirements/
├── scope.md                      맨 위에 "상태: 확정"
└── requirements.md               맨 위에 "상태: 작성 중"
```

더하는 약속은 네 가지입니다.

| 약속 | 내용 |
|---|---|
| 공통 규칙 파일 | 묻는 방식처럼 모든 에이전트가 지킬 규칙을 `.claude/rules/sdd.md` 한곳에 둡니다.<br>Claude Code는 세션을 열 때 이 폴더의 파일을 자동으로 읽으므로, 설명서마다 연결하지 않아도 모두 읽습니다.<br>이 파일을 어디에 둘지는 「둘 곳 검토」에서 비교합니다. |
| 문서 상태 | 에이전트가 남기는 문서 맨 위에 상태를 적습니다.<br>작성 중 → 확인 대기 → 확정 |
| 확정된 문서만 읽기 | 다음 단계 에이전트는 상태가 "확정"인 문서만 읽고 시작합니다.<br>(2026-10-24에 "확정은 앞 단계 확정 뒤"로 바꿈. 아래 「에이전트 사이의 약속」) |
| 되돌려 보내기 | 앞 단계 문서에서 문제를 찾으면 직접 고치지 않고, 그 문서를 만든 단계로 되돌려 보냅니다. |

양식 파일(`template.md`)은 에이전트마다 자기가 남길 문서의 양식을 하나씩 둡니다.  
모든 에이전트가 같은 양식을 쓰는 것은 아닙니다. `scope.md` 양식과 `spec.md` 양식은 서로 다릅니다.

인터뷰에서 요건정리로 넘어가는 모습은 이렇습니다.

1. 사람이 `/sdd-interviewer`를 부릅니다.
2. 인터뷰 에이전트는 자료를 먼저 읽고, 공통 규칙대로 추천을 붙여 묻습니다.
3. 양식대로 `scope.md`를 채웁니다. 상태는 "작성 중"입니다.
4. 다 쓰면 상태를 "확인 대기"로 바꾸고, 사람에게 확인을 요청합니다.
5. 사람이 확인하면 상태가 "확정"이 됩니다.
6. 사람이 `/sdd-analyst`를 부르면, 요건정리 에이전트는 `scope.md`의 상태부터 봅니다.  
   확정이 아니면 시작하지 않습니다.
7. 요건정리 중에 `scope.md`의 문제를 찾으면, 고치지 않고 인터뷰로 되돌려 보냅니다.

| 구분 | 내용 |
|---|---|
| 장점 | 앞 단계 문서가 사람 확인을 거쳐 다음 단계로 이어집니다.<br>공통 규칙은 한곳에서만 고치면 됩니다.<br>설명서는 하는 일에 맞게 짧게 쓸 수 있습니다. |
| 단점 | 설명서마다 목차가 달라서, 처음 읽는 사람은 파일마다 구조를 새로 봐야 합니다. 이 점은 사람이 읽는 설명을 에이전트마다 ADR에 같은 틀로 남겨서 보완합니다.<br>문서마다 상태를 바꿔 줘야 합니다. 상태는 에이전트가 바꾸고, 사람은 확인했다고 말하기만 하면 됩니다. |
| 결과 | 일곱 조건을 모두 지킵니다. |

### 안 4. 안 3에 더해, 모든 설명서를 같은 목차로 쓰기

```
SKILL.md (모든 에이전트가 같음)
  1. 하는 일
  2. 읽는 것
  3. 남기는 것
  4. 순서
  5. 사람 확인
  6. 지킬 것
  7. 다음 단계로 넘기기
```

| 구분 | 내용 |
|---|---|
| 장점 | 어느 설명서든 같은 자리에서 같은 내용을 찾을 수 있습니다. |
| 단점 | 하는 일이 다른 에이전트를 한 틀에 맞추게 됩니다. 혼자 돌고 보고만 하는 QA 에이전트의 설명서에 "사람 확인" 절이 빈 채로 남는 식입니다.<br>사람이 읽을 같은 틀은 에이전트마다 쓰는 ADR이 이미 맡고 있어서 겹칩니다. |
| 결과 | 조건 1~6은 지킵니다.<br>설명서를 일에 맞게 쓰기 어려워서 조건 7은 지키지 못합니다. |

### 안 5. 안 4에 더해, 새 에이전트를 만들어 주는 스킬 두기

## 결정

안 3을 제안합니다.  
일곱 조건을 모두 지키는 안은 안 3뿐입니다.  
같은 목차(안 4)와 에이전트를 만들어 주는 스킬(안 5)은 에이전트를 몇 개 만들어 본 뒤, 실제로 필요해지면 다시 봅니다.

**만드는 절차**

에이전트 하나를 만들 때마다 이 순서를 따릅니다.

1. 그 에이전트의 ADR을 씁니다.  
   ADR의 「결정」은 아래 「에이전트 ADR에 쓸 것」 순서대로 씁니다.
2. 시험 장면을 3개 이상 정하고 ADR에 적습니다.  
   장면마다 무엇이 나오면 통과인지 확인할 수 있게 씁니다.
3. 에이전트 설명서와 양식 파일을 씁니다.
4. 시험 장면대로 실제로 구동해 보고, 사람이 결과를 확인합니다.
5. 통과하지 못한 곳을 고치고 다시 구동합니다.  
   통과하면 커밋합니다.

2번은 공식 문서가 권하는 "시험 장면 먼저"를 따른 것입니다.  
무엇이 되어야 하는지부터 정해 두면, 지침도 필요한 만큼만 쓰게 됩니다.

**에이전트 ADR에 쓸 것**

설명서의 목차는 에이전트마다 다르지만, 사람이 읽는 ADR은 같은 순서로 씁니다.  
그래서 어느 에이전트든 ADR을 읽으면 같은 순서로 이해할 수 있습니다.

1. 하는 일 (하지 않는 일도 함께)
2. 읽는 것
3. 남기는 것 (양식)
4. 대화 순서 (실행형은 일하는 순서)
5. 사람 확인
6. 지킬 것
7. 다음 단계로 넘기기
8. 시험 장면

**폴더와 이름**

자리 ③으로 정합니다.  
④는 모양이 가장 깔끔하지만, 약속을 늘 읽히게 하는 일과 실행형 에이전트 설정에서 개발 흐름에 지장이 큽니다.  
대회가 끝난 뒤 다른 프로젝트에도 가져가고 싶어지면 그때 다시 봅니다.

```
.claude/
├── rules/
│   └── sdd.md               에이전트 사이의 약속
├── skills/
│   ├── handoff-show/        (개발 흐름과 상관없는 스킬)
│   ├── handoff-write/
│   ├── sdd-interviewer/     대화형 6개
│   ├── sdd-analyst/
│   ├── sdd-architect/
│   ├── sdd-designer/
│   ├── sdd-spec-writer/
│   └── sdd-planner/
└── agents/
    └── sdd/                 실행형 4개
        ├── backend-developer.md
        ├── frontend-developer.md
        ├── reviewer.md
        └── tester.md
```

- 대화형은 `/sdd-interviewer`처럼 이름으로 부릅니다. 명령 목록에서도 한데 모여 보입니다.
- 실행형은 부를 때 쓰는 이름(`name`)에도 `sdd-`를 붙입니다(예: `sdd-tester`).  
  Claude Code는 폴더가 아니라 `name`으로 에이전트를 구분하기 때문입니다.
- `harness/`에는 지금처럼 모든 작업에서 늘 지킬 규칙만 둡니다.
- 셋 모두 `.claude/` 안에 있어서, ADR-001의 "Claude Code용 파일은 `.claude/`에"와도 맞습니다.

실제 개발 팀의 직함처럼 읽혀서, 이름만 보고도 무엇을 맡은 에이전트인지 알 수 있습니다.

- 대화형을 스킬로 두는 이유는 서브에이전트에서는 사용자에게 질문하는 도구가 빠지기 때문입니다.  
  사람과 주고받아야 하는 단계는 메인 대화에서 도는 스킬이어야 합니다. ADR-002의 나눔이 공식 문서와도 맞습니다.
- 이름은 영어 소문자, 숫자, 하이픈으로 쓰고, 앞에 `sdd-`를 붙입니다. 이름은 위 「에이전트 이름」 표를 따릅니다.
- `description`에는 무엇을 하는지와 언제 쓰는지를 함께 씁니다.
- 대화형은 사람이 `/이름`으로 부르거나, 앞뒤 단계에서 넘어가야 할 때 Claude가 사람에게 한 번 묻고 부릅니다.  
  처음에는 사람이 부를 때만 시작하도록 `disable-model-invocation: true`를 두었습니다.  
  2026-10-24 아키텍처 에이전트를 구동해 보니, 아키텍처가 요건을 되돌려 보낼 때마다 사람이 `/sdd-analyst`를 따로 불러야 해서 번거롭고 느렸습니다.  
  그래서 이 설정을 빼고, 약속에 "한 번 묻고 부른다"와 "묻지 않은 일에 부르지 않는다"를 더했습니다. 확정과 승인은 그대로 사람이 합니다.
- 실행형은 역할에 필요한 도구만 `tools`에 둡니다.

**설명서 쓰는 법**

- 목차와 쓰는 방식은 그 에이전트가 하는 일에 맞게 정합니다.
- 500줄 이하로 두고, 길어지는 내용은 같은 폴더의 파일로 빼서 한 번만 연결합니다.
- 대화가 길어져 앞 내용을 줄일 때, 설명서는 앞부분만 남을 수 있습니다(공식 문서).  
  그래서 가장 중요한 지시를 맨 앞에 둡니다.
- 파일 안의 경로는 슬래시(`/`)로 씁니다.

**에이전트 사이의 약속**

`.claude/rules/sdd.md`에 담을 것은 두 묶음입니다.

- 묻는 방식
  - 앞 단계 문서와 자료부터 읽고, 정해진 것은 다시 묻지 않습니다.
  - 물을 때는 선택지로 묻고, 추천과 근거를 붙입니다.
  - 근거가 없는 것은 짐작으로 채우지 않고 「질문 대기」로 남깁니다.
- 문서와 단계 잇기
  - 사람이 읽는 문서는 업무 말로 씁니다.
  - 문서 맨 위에 상태를 적습니다: 작성 중 → 확인 대기 → 확정
  - 확정은 사람이 확인했다고 말할 때만 합니다.
  - 확정되면 다음에 부를 단계를 알려 줍니다. 다음 단계는 설명서마다 적고, 흐름 전체는 `docs/guide/sdd.md`에 둡니다.
  - 앞 단계 문서가 확정되기 전에도 초안은 쓸 수 있습니다. 내 문서의 확정은 읽은 앞 단계 문서가 모두 확정된 뒤에만 합니다.
  - 확정된 문서를 고치면 상태를 확인 대기로 되돌리고 다시 확인받습니다.
  - 앞 단계 문서에서 문제를 찾으면 직접 고치지 않고, 그 문서를 만든 단계로 되돌려 보냅니다.
  - 앞 단계 문서를 읽으면, 그 문서의 상태(확정이면 확정 날짜)와 읽은 때의 커밋을 내 문서에 적습니다.
  - 앞 단계 문서가 읽은 때의 커밋 뒤에 바뀌었으면, 비교해 바뀐 곳을 먼저 보여 주고, 걸리는 곳만 고칩니다.

2026-10-23에 인터뷰 에이전트를 만들면서 약속을 다시 봤습니다.

- 시작할 때 할 일과 하지 않을 일을 알리는 것은 인터뷰 설명서로 옮겼습니다. 단계마다 하면 흐름이 번거로워집니다.
- 한 번에 4개까지만 묻는다는 약속은 뺐습니다. 질문 도구가 이미 한 번에 4개까지만 받습니다.
- 단계마다 얼마나 묻는지는 약속이 아니라 설명서에서 정합니다.  
  인터뷰는 묻는 단계이고, 아키텍처부터는 초안을 보여 주고 승인받는 쪽에 가깝게 만듭니다.
- 「열린 질문」은 앞으로 물을 질문이라는 뜻이 드러나게 「질문 대기」로 바꿨습니다.
- 확정되면 다음 단계를 알려 주는 약속을 더했습니다. 단계 사이를 자연스럽게 넘어가기 위해서입니다.

같은 날 요건정리 에이전트를 만들면서(ADR-005) 바뀐 곳만 다시 보는 약속을 더했습니다.

- 범위가 확정된 뒤에도 고쳐질 수 있는데, 다음 단계는 무엇이 바뀌었는지 알 길이 없었습니다.
- 그래서 읽은 문서의 확정 날짜와 커밋을 남기고, 다시 확정되었으면 그때와 비교(git diff)해 걸리는 곳만 고칩니다.
- 바뀐 내용을 따로 적는 칸을 앞 단계 문서에 두는 방법도 있었지만, git이 이미 기록하고 있어서 앞 단계에 일을 더 얹지 않았습니다.
- 요건이 바뀌면 아키텍처, 디자인, 스펙도 같은 일을 겪으므로 설명서마다가 아니라 약속에 둡니다.

2026-10-24에 아키텍처 에이전트를 만들면서(ADR-006) 확정된 문서만 읽는 약속을 바꿨습니다.

- 요건은 탭 7개 초안을 모두 썼지만 팀 검토 중이라 모두 작성 중이었고, 마감은 짧았습니다.  
  확정된 문서만 읽으면 아키텍처를 시작할 수 없었습니다.
- 그래서 앞 단계가 확정되기 전에도 초안은 쓸 수 있게 하고, 확정만 앞 단계 확정 뒤에 하게 했습니다.  
  확정되지 않은 문서 위에서 뒤 단계가 먼저 굳지 않게 하기 위해서입니다.
- 확정 전 문서는 확정 날짜가 없으므로, 바뀐 것을 알아채는 기준을 "다시 확정됨"에서 "읽은 때의 커밋과 다름"으로 바꿨습니다.
- 약속은 "쓸 수 있다"이므로 단계마다 더 엄격하게 둘 수 있습니다. 요건정리는 범위가 확정되어야 시작합니다(ADR-005).

## 주의할 점

- `.claude/rules/sdd.md`는 CLAUDE.md처럼 모든 세션에 올라갑니다.  
  공식 문서는 CLAUDE.md를 200줄 이하로 두라고 권하고, 규칙 파일도 길면 세션을 열 때 경고가 뜹니다.  
  그래서 짧게 유지합니다.
- 실행형 에이전트에는 프로젝트 지침을 읽지 않게 하는 옵션(`omitClaudeMd`)을 쓰지 않습니다.  
  쓰면 에이전트 사이의 약속도 함께 빠질 수 있습니다.
- 이 ADR을 채택하면 README의 폴더 설명에 `.claude/rules/`를 더합니다.
- 이 방식은 인터뷰 에이전트를 만들면서 처음 써 봅니다.  
  맞지 않는 곳이 나오면 이 ADR을 고친 뒤 채택합니다.
- 시험을 자동으로 돌리는 공식 도구(skill-creator 플러그인)가 있습니다.  
  처음에는 손으로 구동해 보고, 되풀이가 많아지면 쓸지 정합니다.
