# ADR-016 시연 초기 데이터는 실제 에이전트 판별 결과를 스냅샷 SQL로 저장해 불러온다

- 상태: 채택
- 날짜: 2026-11-03

## 요약

데이터 초기화 때 들어가는 상담(과거 이력 14일 280건 + 시드 통화 25건)을 실제 장애 알림 에이전트로 판별한 결과를 `backend/sql/16_demo_snapshot.sql` 로 저장하고, 초기화와 빈 DB 생성 때 이 파일을 불러옵니다.  
불러올 때 마지막 날이 '불러오는 날의 전날'이 되도록 시각과 통화 ID 날짜(`CALL-MMDD-NN`)를 옮깁니다.  
스냅샷은 `backend/scripts/build_demo_snapshot.py` 로 다시 만듭니다.

## 배경

- 지금까지 과거 이력은 `history_seed.py` 가 에이전트를 실제로 돌리지 않고 결과 형식만 흉내 내 기록했습니다. 판별 로직(같은 원인 묶기, P1 상한 등, ADR-015)이 바뀌어도 과거 이력에는 반영되지 않았습니다.
- 시연 화면의 과거 이력·모니터·유사 사례가 실제 에이전트가 낸 결과여야 설명과 맞습니다.
- 초기화할 때마다 에이전트를 돌리면 LLM 호출이 수백 번이라 수십 분이 걸리고 비용이 듭니다(305건 기준 로컬 약 40분).

## 검토한 안

| 안 | 내용 | 단점 |
|---|---|---|
| 안 1 | 지금처럼 흉내 낸 결과 | 실제 판별과 다를 수 있음 |
| 안 2 | 초기화 때마다 실제 에이전트 실행 | 수십 분·LLM 비용, 결과가 매번 달라짐 |
| 안 3 (고른 안) | 한 번 실제로 돌린 결과를 SQL 스냅샷으로 저장, 불러올 때 날짜만 옮김 | 판별 로직이 바뀌면 스냅샷을 다시 만들어야 함. 3.6MB SQL 파일 |

## 결정

- 안 3으로 정했습니다.
- 만드는 방법(`build_demo_snapshot.py`)
  - 상담을 등록 시각 순으로 실제 그래프로 판별하고, 그 실행이 만든 기록의 시각을 상담 등록 시각으로 옮깁니다. 메신저는 MOCK 입니다.
  - 같은 증상 묶기(최근 60분)와 개선의견의 관련 장애 찾기(최근 며칠)는 '지금'이 아니라 '상담 등록 시각'을 기준으로 봅니다(`find_open_incidents`, `recent_incidents_for_link` 의 `at`). 실시간 등록에서는 두 시각이 같아 동작이 바뀌지 않습니다.
  - 하루가 끝날 때마다 그날 과거 이력 장애에 담당자 처리(IT담당자 처리완료, 센터관리자 관찰 확인·수동 알림·미대상/오탐 종결)를 `history_seed.py` 와 같은 규칙으로 붙입니다. 해결된 장애는 다음 날 상담의 과거 사례가 됩니다.
  - 시드 통화(02·11)는 전날 저녁으로 옮겨 판별하고, 담당자 처리 없이 열린 채로 둡니다.
- 불러오는 방법(`db_init`)
  - 스냅샷 파일이 있으면 초기화 때 시드 SQL(기본 직원·고객 되살리기용)을 실행한 뒤 시연 표를 비우고 스냅샷을 넣습니다. 없으면 예전 방식(과거 이력 생성기 + 시드 통화 상태만 완료)입니다.
  - 빈 DB에서는 과거 이력이 없을 때만 스냅샷을 넣습니다(계정 초기화 등으로 다시 실행돼도 쓰던 데이터는 그대로).
  - 메시지 본문·실행 메시지 안에 글자로 쓴 날짜는 옮기지 않습니다.

## 결과

- 데이터: `backend/sql/16_demo_snapshot.sql` — 2026-11-02 기준 과거 이력 10/19~11/1, 실행 305건(LLM 판별), 장애 128건, 메신저 기록 80건(MOCK), 대규모 장애 5건 모두 독립 고객 3명 → P1

- 판별 로직·판별기준·시나리오를 바꾸면 `venv/Scripts/python.exe scripts/build_demo_snapshot.py` 로 스냅샷을 다시 만들어 커밋합니다(로컬 시연 데이터를 지우고 다시 만듦, LLM 사용 시 40분 안팎).
