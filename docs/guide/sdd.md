# SDD 한눈에 보기

우리 팀이 요건과 설계를 정할 때 쓰는 흐름과 개발 에이전트 10개를 한 장에 모았습니다.  
SDD는 스펙 주도 개발(Spec-Driven Development)의 줄임말입니다.  
요건과 설계는 사람이 먼저 정하고, AI는 그대로 구현하고 검증하는 일을 돕습니다.

- 왜 이렇게 정했는지는 [ADR-002](../adr/ADR-002-dev-flow-and-agents.md)(흐름)와 [ADR-003](../adr/ADR-003-how-to-build-agents.md)(만드는 방식과 이름)에 있습니다.
- 이 저장소의 앱 코드는 이 흐름으로 만든 것이 아니라 개발 담당이 따로 만들었습니다([ADR-010](../adr/ADR-010-submission-implementation.md)). 요건 대비 구현 현황은 요건마다 제출 코드의 구현 여부와 근거를 추적한 표이고, 이 흐름의 검증 단계(⑦) 산출물 역할을 합니다. 아키텍처·배포 문서와 이 표는 완성된 코드를 읽고 나중에 정리한 것입니다.
- 이 문서는 지금 상태를 보여 줍니다. 에이전트를 만들거나 흐름이 바뀌면 같이 고칩니다.
- 여기서 말하는 에이전트는 개발할 때 쓰는 도구입니다. 제품 안에서 장애를 찾는 AI 에이전트와는 다릅니다.
- 10개 가운데 4개(인터뷰, 요건정리, 아키텍처, 디자인)를 만들었고, 나머지 6개는 만들지 않았습니다(이유는 [ADR-009](../adr/ADR-009-build-without-spec-agents.md)). 만든 4개는 `.claude/skills/`에 있습니다.

## 흐름

```
인터뷰 ── ① 범위 확인
  ↓
요건정리 ── ② 요건 확정
  ↓
  ├→ 아키텍처 ── ③ 아키텍처 승인
  └→ 디자인 ── ④ 디자인 승인
  ↓ (③과 ④가 모두 끝나면)
스펙 ── ⑤ 스펙 승인
  ↓
구현 계획 ── ⑥ 계획 승인
  ↓
구현
  ↓
검증 ── ⑦ 화면 확인
  ↓
배포·기록
```

①~⑦은 AI 작업 후 사람이 확인하는 곳입니다.  
확인을 마쳐야 다음 단계로 진행합니다.

| 확인 | 무엇을 확인하나 |
|---|---|
| ① 범위 확인 | 인터뷰를 한 사람이나 팀원이 `scope.md`를 확인해야 요건정리를 시작합니다. |
| ② 요건 확정 | 요건을 정리한 사람이 먼저 보고, 팀 회의에서 팀원이 확인합니다. |
| ③ 아키텍처 승인 | 아키텍처를 승인해야 스펙을 씁니다. |
| ④ 디자인 승인 | 화면 규칙과 그 탭의 시안을 승인해야 스펙을 씁니다. |
| ⑤ 스펙 승인 | 스펙을 승인해야 구현 계획을 씁니다. |
| ⑥ 계획 승인 | `plan.md`를 승인해야 구현을 맡깁니다. |
| ⑦ 화면 확인 | 코드 리뷰와 QA가 끝나면 사람이 배포된 화면을 직접 눌러 봅니다. |

## 에이전트 10개

### 대화형 6개

사람과 대화하며 문서를 만듭니다.  
사람이 `/이름`으로 부르거나, 앞뒤 단계로 넘어가야 할 때 Claude가 한 번 묻고 부릅니다.  
끝날 때 사람이 확정하거나 승인합니다.

| 에이전트 | 부르는 법 | 하는 일 | 읽는 것 | 남기는 것 | 만들었나 |
|---|---|---|---|---|---|
| 인터뷰 | `/sdd-interviewer` | 범위와 큰 갈림길을 정합니다. | 팀이 가진 자료(v2 요건정의서, 회의 기록 등) | `docs/requirements/scope.md` | 있음 |
| 요건정리 | `/sdd-analyst` | 화면 탭별로 요건을 자세히 씁니다. | `scope.md` | `docs/requirements/requirements.md`<br>`docs/requirements/tabs/` (탭마다 파일) | 있음 |
| 아키텍처 | `/sdd-architect` | 여러 탭이 같이 쓰는 것을 한곳에서 정합니다. | 요건정의서 | `docs/architecture/architecture.md` | 있음 |
| 디자인 | `/sdd-designer` | 화면 규칙을 정하고 탭마다 시안을 만듭니다. | 요건정의서 | `docs/design/style-guide.md`<br>`docs/design/mockups/` | 있음 |
| 스펙 | `/sdd-spec-writer` | 탭이 어떻게 동작해야 하는지 정합니다. | 요건정의서, 아키텍처, 화면 규칙과 그 탭의 시안 | `docs/spec/spec.md` | 아직 |
| 구현 계획 | `/sdd-planner` | 지금 코드를 읽고 어떻게 만들지 변경 전과 후를 보여 줍니다. | 요건정의서, 아키텍처, 화면 규칙과 그 탭의 시안, 스펙, 지금 코드, 기술 스택 ADR | `docs/plan/plan.md` | 아직 |

### 실행형 4개

맡기면 혼자 끝까지 하고 결과를 보고합니다.  
Claude가 일을 맡길 때 아래 이름으로 부릅니다.

| 에이전트 | 이름 | 하는 일 | 남기는 것 | 만들었나 |
|---|---|---|---|---|
| 백엔드 구현 | `sdd-backend-developer` | `plan.md`대로 서버 쪽 코드를 만듭니다. | 코드 | 아직 |
| 프론트 구현 | `sdd-frontend-developer` | `plan.md`대로 화면 코드를 만듭니다. | 코드 | 아직 |
| 코드 리뷰 | `sdd-reviewer` | 코드 품질을 봅니다. | `docs/verification/review.md` | 아직 |
| QA | `sdd-tester` | 실제로 동작하는지 봅니다. | `docs/verification/qa.md` | 아직 |

- 테스트 항목(`docs/verification/test.md`)을 구현과 QA 중 누가 만들지는 아직 정하지 않았습니다.
- 배포·기록 단계는 에이전트를 따로 두지 않고 axhub 배포 기능을 씁니다. 기록은 `docs/deploy/deploy.md`에 남깁니다.

### 이름과 자리

- 영어 이름은 ADR-003에서 정한 이름입니다. ADR-003이 바뀌면 이 표도 고칩니다.
- 대화형은 `.claude/skills/sdd-<이름>/SKILL.md`, 실행형은 `.claude/agents/sdd/<이름>.md`에 둡니다.
- 폴더와 파일은 에이전트를 하나씩 만들 때 생깁니다.  
  ADR-003의 절차(ADR → 시험 장면 → 설명서 → 구동)를 거쳐 만들고, 만들면 위 표의 「만들었나」를 "있음"으로 바꿉니다.

## 자주 헷갈리는 것

### 요건정리, 아키텍처, 디자인, 스펙, 구현 계획은 무엇이 다른가

"장애 목록" 탭을 예로 들면 단계마다 묻는 질문이 다릅니다.  
예시는 설명을 위해 지어낸 것입니다.

| 단계 | 묻는 질문 | 예 |
|---|---|---|
| 요건정리 | 누가 무엇을 할 수 있어야 하나 | IT 담당자는 처리하지 않은 장애를 급한 것부터 볼 수 있어야 한다. 급한 정도는 등급으로 정하고, 같은 등급이면 먼저 들어온 것이 먼저다. |
| 아키텍처 | 여러 탭이 같이 쓰는 것은 무엇인가 | 장애 정보에는 제목, 심각도, 신고 시각이 들어 있다. |
| 디자인 | 화면이 어떻게 보이나 | 장애 목록은 카드 모양이고, 심각도는 색으로 구분한다. |
| 스펙 | 이 탭이 어떻게 동작해야 하나 | 심각도로 거를 수 있다. 카드를 누르면 상세가 열린다. 장애가 없으면 "없음"이라고 보여 준다. 화면은 서버에 무엇을 요청하고 무엇을 받는다. |
| 구현 계획 | 그것을 코드로 어떻게 만드나 | 이 파일을 새로 만들고, 저 파일은 이렇게 바꾼다. (변경 전과 후) |

요건은 사람이 이루려는 일과 지켜야 할 규칙입니다.  
아키텍처는 공통 뼈대이고, 디자인은 겉모습입니다.  
스펙은 둘을 합쳐 탭 하나의 약속을 만들고, 구현 계획은 그 약속을 코드로 어떻게 지킬지 정합니다.

요건과 설계의 경계는 이렇게 판단합니다(ADR-005).  
비개발자가 회의에서 "맞다, 아니다"를 말할 수 있으면 요건입니다.  
같은 요건을 화면 조작이나 데이터로 여러 방법으로 만들 수 있다면, 그 방법은 뒤 단계에서 정합니다.

### 대화형과 실행형은 왜 나눴나

대화형은 사람에게 묻고 확인받아야 해서, 메인 대화에서 도는 스킬로 둡니다.  
서브에이전트에서는 사용자에게 질문하는 도구가 빠지기 때문입니다(ADR-003).

실행형은 정해진 일을 혼자 끝까지 하는 서브에이전트입니다.  
구현하는 에이전트와 확인하는 에이전트를 나눠서, 만든 쪽이 스스로 검사하지 않게 합니다(ADR-002).

### design은 무엇을 뜻하나

이 저장소에서 design은 화면 디자인만 뜻합니다.  
시스템을 어떻게 나눌지는 "아키텍처", 탭이 어떻게 동작할지는 "스펙"이라고 부릅니다.  
ADR-001의 `design/` 폴더는 설계를 뜻했는데, 지금은 이름이 `docs/spec/`으로 바뀌었습니다.

### 단계를 탭마다 하나, 전체를 한 번에 하나

에이전트에 정해 두지 않습니다.  
전체를 한 번에 하거나, 한 번에 해 두고 탭마다 보거나, 처음부터 탭마다 하는 것 중에서 그때그때 대화로 정합니다(ADR-002).

### 앞 단계 문서에서 문제를 찾으면

직접 고치지 않고, 그 문서를 만든 단계로 되돌려 보냅니다(ADR-003).  
아키텍처와 시안이 서로 어긋날 때도 같습니다. 어긋난 쪽 단계로 돌아가 고치고 다시 승인받습니다(ADR-002).

## 이 문서를 고치는 때

- 에이전트를 하나 만들면 「만들었나」를 "있음"으로 바꿉니다.
- 흐름이나 이름이 바뀌면 ADR을 먼저 고치고, 이 문서를 거기에 맞춥니다.
